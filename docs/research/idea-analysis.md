# Build Toolsmith as a tool workshop, not a browser

Toolsmith is a sound idea if it is positioned as **a local MCP server plus a governed workshop for agent-built site tools**, and a bad idea if it is positioned as "an agentic browser." The problem is real: as of September 2026 the open web outside Shopify has essentially no site-declared WebMCP tools (a May 2026 crawl found **0 of 111,076 top domains**), so agents re-explore every site on every run at roughly **$0.07–$0.40 per ten-step task**, while a saved tool costs about a cent or nothing on replay. Every individual piece of Toolsmith already exists somewhere (Chrome's DevTools pane inspects, five-plus bridges relay page tools to Claude Code, Stagehand and Skyvern cache agent runs as code), but nobody ships the combination that matters: agent-authored tools in WebMCP's own shape, persisted and versioned locally, with human review, per-tool disable and rollback, served to Claude Code, Codex and Cursor over one local MCP server. The closest analogue, DeepDeck, is five weeks old with 26 stars and welded to DeepSeek Harness. The bets that could sink it are concrete: WebMCP is Chromium-only and its origin trial ends **2026-11-17** with no ship commitment; generated tool code shares the user's origin and cookies, so exfiltration is the top security risk; the academic record says agent-built tools pay off only through repeated reuse; and Anthropic has banned every form of subscription intermediation except spawning the unmodified `claude` binary. Design around those four and the project is both buildable by one senior frontend engineer and a credible portfolio piece, because the durable value, structured actions on sites that will never author their own, does not depend on the standard winning.

## The problem is real, but the buyer is a developer running Claude Code

Demand for browser agents is large and still compounding. `browser-use/browser-use` sits at **115,959 GitHub stars** gaining roughly 2,000 a week, and its newest repo `jev-ultrafast`, pitched as the "fastest and cheapest web agent," collected **18,161 stars in its first week** ([GitHub](https://github.com/browser-use/jev-ultrafast); [star-history](https://www.star-history.com/browser-use/browser-use/)). That velocity is the tell: the market's present pain is cost and speed, not raw capability, which is exactly what tool reuse attacks. A visible sub-demand for "record once, make the site a tool" already exists in `workflow-use` (4,184 stars, still labelled "very early development ... we don't recommend using this in production"), `webpage-mcp`, Anysite MCP and Apify's website-to-MCP tool ([workflow-use README](https://raw.githubusercontent.com/browser-use/workflow-use/main/README.md); [webpage-mcp](https://github.com/mcpland/webpage-mcp); [Apify](https://apify.com/clever_fashion/mcp-website-tool)).

The consumer slot is closed. Claude in Chrome went GA on every paid plan on **2026-08-26** with scheduled tasks and workflow recording ([Claude blog](https://claude.com/blog/claude-in-chrome-generally-available); [support.claude.com](https://support.claude.com/en/articles/12012173-get-started-with-claude-in-chrome)); third-party trackers put its install base at 9–15 million, a figure the research could not verify against the store. OpenAI killed its standalone Atlas browser after nine and a half months, folding agentic browsing into the ChatGPT desktop app and a Chrome extension ([The Register](https://www.theregister.com/ai-and-ml/2026/07/10/openais-atlas-browser-doesnt-make-it-to-its-first-birthday/5269818)), Atlassian bought The Browser Company for ~$610M ([Business Wire](https://www.businesswire.com/news/home/20250904645125/en/Atlassian-Enters-Into-Definitive-Agreement-to-Acquire-The-Browser-Company-of-New-York)), and Edge retired Copilot Mode into the base browser ([gHacks](https://www.ghacks.net/2026/05/15/microsoft-edge-retires-copilot-mode-and-integrates-ai-features-across-desktop-and-mobile/)). Even OpenAI abandoned the standalone-browser form factor; a solo Electron app competing on general browsing enters a window that has already shut.

The developer side is the opposite: it is fragmenting, not consolidating. Playwright MCP (37,484 stars), Chrome DevTools MCP (52,489), Stagehand (25,222), Skyvern (23,055), BrowserOS (13,738) and the WebMCP bridge extensions all coexist, and coding agents are the buyer ([GitHub API reads in the competitive note](https://github.com/ChromeDevTools/chrome-devtools-mcp)). Consumers will never review, disable or roll back a tool. A developer or technical ops person who already runs Claude Code or Codex and wants a site without an API to become a callable, cost-capped, reviewable tool is the only user who values the governance layer, and that is the user Toolsmith should be built for. One caveat the research could not resolve: no HN or Reddit thread text was retrievable, so the frustration signal is inferred from repo velocity and product positioning rather than quoted complaints.

## Every piece exists; nobody ships governed tools over MCP

The inspect and bridge layers are commoditised. Chrome DevTools ships a WebMCP pane with "Available Tools" and "Invoked Tools" ([Chrome DevTools docs](https://developer.chrome.com/docs/devtools/application/webmcp)), Google's own utilities repo has an inspector extension and evaluation CLI ([GoogleChromeLabs/webmcp-tools](https://github.com/GoogleChromeLabs/webmcp-tools)), and at least five independent projects relay page tools to Claude Code and Cursor: the MCP-B local relay, `webmcp-cdp-bridge`, WebMCP Bridge, `mcp-webmcp`, and `@mcp-b/chrome-devtools-mcp` ([WebMCP-org README](https://raw.githubusercontent.com/WebMCP-org/npm-packages/main/README.md); [littleplato/webmcp-cdp-bridge](https://raw.githubusercontent.com/littleplato/webmcp-cdp-bridge/main/README.md)). Every one of them re-fetches `getTools()` on each call; none persists or versions anything. Both Playwright MCP and Chrome DevTools MCP now expose page-registered WebMCP tools natively ([playwright.dev/mcp](https://playwright.dev/mcp/introduction); [tool-reference.md](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)). "Usable by Claude Code over local MCP" is table stakes, not a differentiator.

The synthesise layer has two live products and one research line. **BrowserAct Skill Forge** explores a site once and emits a `SKILL.md` plus Python scripts, "API endpoints first, DOM fallback," for Claude Code, Codex and Cursor ([browser-act/skills README](https://raw.githubusercontent.com/browser-act/skills/main/README.md)). Browserbase's Director records agent steps into "repeatable Stagehand code" on the back of a $40M Series B ([PRNewswire](https://www.prnewswire.com/news-releases/browserbase-launches-director-to-automate-the-web-for-everyone-announces-40m-series-b-302483761.html)). Salesforce's WALT "reverse-engineers latent website functionality into reusable invocable tools" ([arXiv 2510.01524](https://arxiv.org/abs/2510.01524)). None of these emits WebMCP-shaped tools; Skill Forge emits scripts, Director emits Playwright-style code.

**DeepDeck** is the only product that combines a desktop Chromium, WebMCP inspection, a Builder mode and per-site "inspection, disabling, and rollback." Read its README closely, because it is Toolsmith's blueprint and its warning: created **2026-08-17**, **26 stars, 1 fork**, MIT, near-daily releases by a solo maintainer, a Builder that "explores its real controls, tries the relevant workflows, and turns verified operations into tools" (23 tools from X in its screenshot), and a footprint that is entirely Chinese-language with no HN or Product Hunt launch ([jo32/DeepDeck README](https://raw.githubusercontent.com/jo32/DeepDeck/main/README.md); [GitHub API](https://api.github.com/repos/jo32/DeepDeck)). It reuses DeepSeek Harness profiles, credentials and plugins, and the README fetch found no local MCP server for external agents; that last point is an interpretation of the README rather than a verified fact, because the homepage was blocked. Its own caveats, "exploration takes time and tokens," "site changes can require revalidation," "measured savings are not yet established," are the honest state of the art.

The white space, then, is narrow and specific: synthesised tools in WebMCP's own shape so they are interchangeable with site-declared tools the day Chrome ships; a review surface that shows verification evidence (what was tried, on which DOM, with what result) rather than only code; per-tool disable and rollback enforced on the same local MCP server so Claude Code, Codex and Cursor inherit the policy; and a diff between a site-declared tool and a synthesised one when both exist. The nearest prior art for the trust layer is Skyvern's Workflow Version History with block-level visual diff and restore ([Skyvern docs](https://www.skyvern.com/docs/workflows/manage-workflows)) and the Git-backed `self-improving-skills` pattern in the Claude Code ecosystem ([unisone/self-improving-skills](https://github.com/unisone/self-improving-skills)). The risk in that gap is that governance alone is a feature, not a product: Skyvern ships version history as one line item of a $29–$149/month cloud plan ([Skyvern pricing](https://www.skyvern.com/pricing)). Governance has to be attached to the thing users actually want, which is cheap, repeatable actions on sites that have no API.

## WebMCP is a Chromium-only bet with a November 17 deadline

Two numbers describe WebMCP adoption and both are true. freeCodeCamp scanned **111,076 of the top 200,000 domains** in May 2026 and found "exactly zero" shipping WebMCP, "not a single Fortune 500 site" ([freeCodeCamp](https://www.freecodecamp.org/news/a-developers-guide-to-webmcp/)); that scan checked a header rather than runtime `document.modelContext` and predates the trial. Then on **2026-08-21** Shopify auto-enabled ten storefront tools (`search_catalog`, `get_product`, `update_cart`, `proceed_to_checkout` and so on) on every Liquid storefront with no merchant action ([Shopify changelog](https://shopify.dev/changelog/webmcp-liquid-hydrogen)), and OpenAI enabled WebMCP in the ChatGPT desktop browser on **2026-08-25** with Chrome, Cloudflare, Shopify, Vercel, Render and Netlify as launch partners ([Search Engine Journal](https://www.searchenginejournal.com/chatgpt-adds-webmcp-support/587237/)). The self-submitted directories list **131** to **673** sites, mostly indie tools and agent-readiness vendors selling to each other; the `iswebmcp` index describes itself as "partial and uncalibrated" ([iswebmcp README](https://raw.githubusercontent.com/mlmrx/iswebmcp/main/README.md)). Expedia, Booking.com, Target, Instacart, TurboTax, Credit Karma, Redfin and Etsy are "experimenting" in the origin trial ([Developers Digest](https://www.developersdigest.tech/blog/webmcp-google-browser-agent-standard-2026)); none has published a live-tool claim.

The timeline is tight and uncommitted. Chrome's origin trial runs 149 through 156 and **ends 2026-11-17**; Chrome Status pencils in Chrome 157 (2026-11-03) as the "anticipated" milestone, "a target rather than a committed ship date" ([assistant-ui issue #7652](https://github.com/assistant-ui/assistant-ui/issues/7652); [Chrome Platform Status](https://chromestatus.com/feature/5117755740913664)). Edge's trial expires the same day ([Edge origin trials](https://developer.microsoft.com/en-us/microsoft-edge/origin-trials/trials/0b76fe60-b266-458e-a285-04e375c0c31a)). Google said at I/O that "Gemini in Chrome will soon support WebMCP APIs" and as of mid-September the consuming agent has not shipped ([Chrome at I/O 26](https://developer.chrome.com/blog/chrome-at-io26)). **WebKit formally opposes** (issue #670: "we do not think a parallel agent-facing tool layer is the right solution") and Mozilla is neutral ([WebKit/standards-positions#670](https://github.com/WebKit/standards-positions/issues/670); [mozilla/standards-positions#1412](https://github.com/mozilla/standards-positions/issues/1412)). The API itself moved from `navigator.modelContext` to `document.modelContext` on 2026-07-21, which broke mocked test suites that registered nothing in real Chrome ([webmcp README](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/README.md); [ModelPiper](https://modelpiper.com/blog/webmcp-chrome-api-migration-mocked-tests)). The spec is a Community Group draft, "not a W3C Standard nor on the W3C Standards Track" ([spec](https://webmachinelearning.github.io/webmcp/)).

The precedents are sobering. Web Bluetooth has been "the future" since Chrome shipped it in 2017 and stays niche because Safari and Firefox refused ([codecrispi.es](https://codecrispi.es/blog/web-bluetooth-2026/)); Web Share, which every engine ships, is on **6.6% of pages** after eight years ([Web Almanac 2025](https://almanac.httparchive.org/en/2025/capabilities)); llms.txt, a zero-cost text file, reached ~9–10% of top sites in 18 months mostly through vendor push ([Rankability](https://www.rankability.com/data/llms-txt-adoption/)). Capability APIs spread when a platform default flips them on (Shopify, WooCommerce, Vercel templates), not through site-by-site authoring. The developer criticism explains why: WebMCP "demands developer effort like server-side MCP but routes through the browser, creating a second-class copy that drifts from the UI" ([The WebMCP False Economy](https://manveerc.substack.com/p/webmcp-false-economy-server-side-mcp-browser-apis)), and Chrome's own guidance concedes prompt injection "appears to be a largely unsolved issue" ([webmcp#11](https://github.com/webmachinelearning/webmcp/issues/11)).

What this means for Toolsmith is a two-sided conclusion. The base case through September 2027 is that Chrome ships around 157–160, Gemini in Chrome and Edge start calling tools, Shopify plus a few platforms account for almost all tool-bearing pages, and independently authored tools stay well under 1% of top sites. That keeps the premise "most sites have no tools, so users need a builder" true for the long tail and for every bespoke enterprise and SaaS app, which is where the value is highest. The risk case, a second trial extension or a stall into a Chromium niche, only hurts if WebMCP is the thesis. So it must not be: treat `document.modelContext` as **one output target** (with the `@mcp-b/global` polyfill for non-trial contexts) and the durable product as structured, reviewable actions over any page. Consuming native tools when a site declares them keeps Toolsmith forward-compatible; synthesising them when it does not keeps it useful either way. Several indie projects already do "scan a site, generate tools, inject via extension" (webmcp-forge, WebMCP Today, WebMCP Extension), none with visible traction ([awesome-webmcp](https://raw.githubusercontent.com/webfuse-com/awesome-webmcp/main/README.md)), so the space is not empty but it is not claimed.

## Electron reaches the WebMCP CDP domain, but generated code shares the user's origin

Feasibility of the shell is not in doubt; feasibility of a safe Builder is the whole project. Electron 44 ships **Chromium 152.0.7977.54**, inside the 149–156 trial window and after Chrome 149 added the DevTools WebMCP panel, so the `WebMCP` CDP domain almost certainly exists in the binary ([electron v44.0.0](https://github.com/electron/electron/releases/tag/v44.0.0)). The domain exposes `enable` (fires `toolsAdded` for every current tool), `invokeTool(frameId, toolName, input)`, `cancelInvocation`, and `toolsAdded`, `toolsRemoved`, `toolInvoked`, `toolResponded` events; each `Tool` carries `name`, `description`, `inputSchema`, `annotations`, `frameId`, `backendNodeId` and a `stackTrace` ([chromedp/cdproto webmcp](https://pkg.go.dev/github.com/chromedp/cdproto/webmcp)). No one has published a test of driving it from `webContents.debugger`; that is a one-day spike, and it comes first. Origin-trial tokens are the wrong lever: Chrome documents that tokens "should not be relied upon to enable trial features in other browsers, including Chromium and other Chromium-based browsers" ([Chrome origin-trial troubleshooting](https://developer.chrome.com/docs/web-platform/origin-trial-troubleshooting)), and Toolsmith embeds arbitrary sites whose tokens are scoped to their own origins. The only approach that works for every embedded site is enabling the Blink runtime feature by command-line switch (`--enable-blink-features`, exact name to confirm against `runtime_enabled_features.json5` for 152), and accepting Electron's security warning about doing so ([Chromium RuntimeEnabledFeatures](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/platform/RuntimeEnabledFeatures.md)). Three documented constraints shape the architecture: Electron allows one debugger client per target and `detach` fires when DevTools is opened, so the setup routine must be idempotent and the DevTools menu disabled for agent-attached views ([electron debugger docs](https://raw.githubusercontent.com/electron/electron/main/docs/api/debugger.md)); `Page.addScriptToEvaluateOnNewDocument` runs "in every frame upon creation" with no frame filter, so the injected bootstrap must self-gate on `location.origin` or it will register tools inside cross-origin ad iframes ([Crawlex](https://blog.crawlex.net/blog/cdp-add-script-evaluate-trap/)); and keep only `WebMCP`, `Page` and `Runtime` enabled, never `DOM`, because the overhead in CDP comes from heavy domains and evaluate loops, not from being attached ([Lightpanda](https://lightpanda.io/blog/posts/cdp-under-the-hood)).

The security picture starts from one fact: an isolated world "shares the DOM but not the JavaScript heap," and it shares the origin. Generated tool code can read any rendered data, submit forms, read non-HttpOnly cookies, and issue same-origin fetches that carry the user's session; no CSRF token protects against same-origin script. Browser Use's `allowed_domains` was bypassed through `data:` and `blob:` URLs so "a prompt-injected LLM can trivially use data:text/html URLs to exfiltrate credentials, cookies, or page content" ([browser-use issue #4763](https://github.com/browser-use/browser-use/issues/4763)), which shows a hostname allowlist is not enough. Prompt injection is the second risk, and the vendors say it cannot be eliminated: WASP found unhardened agents begin executing injected instructions **16–86%** of the time ([WASP, arXiv 2504.18575](https://arxiv.org/pdf/2504.18575)); Anthropic's Claude in Chrome went from **23.6% to 11.2%** attack success after its first mitigations and, at GA, reports **3.8%** for Opus 5 with no safeguards versus **17.6%** for Opus 4.5, and **0%** once "probes" over web content and an action classifier are added ([Claude for Chrome](https://claude.com/blog/claude-for-chrome); [Claude in Chrome GA](https://claude.com/blog/claude-in-chrome-generally-available)). Google's Gemini in Chrome uses a "User Alignment Critic" that sees "only metadata about the proposed action and not any unfiltered untrustworthy web content" ([SecurityWeek](https://www.securityweek.com/google-fortifies-chrome-agentic-ai-against-indirect-prompt-injection-attacks/)). A WebMCP-specific attack paper describes "Mid-Session Tool Injection": hijacking the tool set via unregistration races and mis-framing tools through `readOnlyHint` and descriptions ([arXiv 2606.06387](https://arxiv.org/abs/2606.06387)). Builder mode makes that attack self-inflicted, because the agent both reads page annotations and writes new ones.

A small app cannot replicate RL hardening, probes or critic models. It can build the deterministic layer, and the notes converge on a specific design. Give generated code no `fetch`, `XMLHttpRequest`, `WebSocket` or `sendBeacon`; expose a Toolsmith-owned `http()` helper that enforces same-origin or a per-tool allowlist and logs every request, frozen with `Object.freeze` before the generated function is evaluated (the heap separation is what makes the seal hold). Statically lint generated source for `eval`, `Function`, `import()`, `document.cookie`, `localStorage` and network globals before injection. Run each tool under an `AbortSignal` timeout and a per-minute invocation cap. Assign the trust class in the app, defaulting every generated tool to `consequential` until a human reviewer flips it to `readOnly` after reading it; never trust the agent's own annotation. Hash the injected bundle with SHA-256, store `{hash, source, version, verified_at, approved_by}`, refuse to inject any source whose hash is not approved, and keep prior versions for rollback. Namespace generated tools (`toolsmith.<site>.<name>`) so they can never shadow a page-native tool. Run the agent in a dedicated Electron `session` partition so it never touches the user's default cookies, and block `data:`, `blob:`, `javascript:` and `file:` navigations outright. Wrap outputs flagged `untrustedContent` in a delimiter and a system note that they are data, mirroring Chrome's base64 isolation ([Chrome agent security](https://developer.chrome.com/docs/agents/security)). A cheap metadata-only critic call, a second model that sees the tool name, arguments and the user's goal but never page content, is implementable with the Claude API and mirrors Google's design. Pin a model floor to a current Claude model, because the 3.8% versus 17.6% gap is the difference between a defensible product and an indefensible one. The research found no published prior art for a "human reviews generated browser-tool code, hashes it, and can roll back" UX; treat it as novel product work, and as the part worth writing about.

The local MCP server is the third exposure and the easiest to get right. The MCP spec says servers "MUST validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks" and "SHOULD bind only to localhost" ([MCP transports spec](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-06-18/basic/transports.mdx)); the TypeScript SDK v2's `createMcpExpressApp({ host, allowedHosts, allowedOrigins })` auto-arms Host and Origin checks for loopback binds but silently skips them for LAN or container hosts ([typescript-sdk](https://github.com/modelcontextprotocol/typescript-sdk); [issue #2843](https://github.com/modelcontextprotocol/typescript-sdk/issues/2843)). Bind `127.0.0.1` only, reject any request carrying an `Origin` header at all (Claude Code, Codex and Cursor are not browsers and send none), require a bearer token from `crypto.randomBytes(32)` on every request including `initialize`, and persist it only through the async `safeStorage` API, which on macOS keys to Keychain and requires a code-signed build; the sync API is gone in Electron 46 ([electron safeStorage docs](https://raw.githubusercontent.com/electron/electron/main/docs/api/safe-storage.md)). Add an integration test that sends `Host: evil.example` and `Origin: https://evil.example` and asserts 403, so an SDK upgrade cannot disarm the check. Backstage shipped an MCP endpoint with no rebinding protection ([backstage issue #35791](https://github.com/backstage/backstage/issues/35791)); this mistake is common.

## Prior art says the test-repair loop works, but only reuse pays for it

The Builder loop, explore, propose, write code, execute to test, repair, store, retrieve, is a well-trodden academic path with consistent lessons. Voyager's Minecraft skill library reached milestones **up to 15.3x faster** than prior systems by storing verified code indexed by description embeddings ([arXiv 2305.16291](https://arxiv.org/abs/2305.16291)). CREATOR's traceback-driven "rectification" stage added roughly **10%** relative accuracy ([ACL Anthology](https://aclanthology.org/2023.findings-emnlp.462/)). ToolMaker's closed install-write-unit-test loop succeeded on **80%** of TM-Bench tasks against **20%** for OpenHands, which suggests the test-repair loop, not model strength, is the main driver of tool-generation success ([ACL 2025](https://aclanthology.org/2025.acl-long.1266.pdf)). On the web specifically, Agent Workflow Memory improved relative success by **24.6% on Mind2Web and 51.1% on WebArena** ([ICML 2025](https://proceedings.mlr.press/v267/wang25bx.html)), and SkillWeaver, the closest analogue to Builder mode, "autonomously discovers skills, executes them for practice, and distills practice experiences into robust APIs" for **31.8%** relative gain on WebArena and **39.8%** on real sites, with weaker agents given a stronger agent's skills improving up to 54.3% ([arXiv 2504.07079](https://arxiv.org/abs/2504.07079)). SkillWeaver's repo encodes the three verification primitives Toolsmith needs: runtime-exception testing, an LLM completion judge, and an `--allow-unverified-apis` flag that defaults to **False** so unverified APIs are never used ([SkillWeaver README](https://raw.githubusercontent.com/OSU-NLP-Group/SkillWeaver/main/README.md)). Microsoft's WebXSkill (April 2026) pairs each skill with "a parameterized action program" and "step-level natural language guidance" so it can run directly or guide an agent when it drifts, worth up to 9.8 points on WebArena ([MSR](https://www.microsoft.com/en-us/research/publication/webxskill-skill-learning-for-autonomous-web-agents/)).

The counter-evidence is the most important finding for the value case. A June 2026 budget-matched study compared AWM, ASI and ReasoningBank against a plain actor given the same total token budget across three WebArena domains and three models, and found the vanilla baseline "matched or surpassed all three augmentation methods in aggregate success rate while often using fewer total tokens"; gains exist "in domains where task structure supports reuse" but "often disappear once augmentation overhead is compared against a budget-matched actor" ([arXiv 2606.15017](https://arxiv.org/abs/2606.15017)). Read plainly: Builder mode does not make a single task more accurate once you charge for the exploration. Its ROI comes from amortising one expensive exploration across many cheap replays, which is precisely what a saved, versioned tool is for and what a chat-style agent never gets. SkillOps adds the maintenance warning: skill libraries accumulate "technical debt" as skills are "added, reused, patched, and linked to changing dependencies," and "self-repairing agents may conflict with external maintenance" ([arXiv 2605.13716](https://arxiv.org/abs/2605.13716)). A Builder that silently self-heals will fight the human's review history; repair must be a proposed patch the reviewer accepts.

Industry converged on the same architecture with the artifact as code rather than a typed tool. Stagehand caches "the selector and supporting metadata," replays "without calling an LLM," and on a mismatch `selfHeal` re-infers and rewrites the cache, with speedups "as high as ~80%" between first and second run ([Browserbase caching](https://www.browserbase.com/blog/stagehand-caching); [stagehand README](https://github.com/browserbase/stagehand)). Skyvern generates and maintains Playwright code while it runs, claims cached runs are **3–5x faster and up to 70% cheaper**, and surfaces a "self-heal panel" showing when recovery fired ([Skyvern changelog](https://www.skyvern.com/blog/skyvern-changelog-july-2026/)). Zapier's AI-built Zaps are drafts that require "human review, field mapping verification, and test execution before activation," with publish replacing the live version and Enterprise able to require approval ([Zapier help](https://help.zapier.com/hc/en-us/articles/9693520498445-Create-Zap-drafts-and-versions)). Nobody publishes replay reliability over time; DeepDeck's "measured savings are not yet established" is the candid version. That absence is an opening: a tool-validity half-life measured across ten real sites over weeks would be the first such number anyone has published.

Verification itself is thin everywhere and Toolsmith can do better cheaply because its artifact is typed. The QA literature is blunt that selector self-healing "genuinely fixes locator drift" but "does not fix timing issues, test data problems, runtime errors, or rendering failures," and one analysis put locator problems at **under a third** of real failures ([Keysight](https://www.keysight.com/blogs/en/tech/software-testing/2026-self-healing-test-automation-beyond-locator-patching)). A WebMCP tool with a declared output schema gives a drift signal selector systems lack: schema-validation failure or empty results. The verification ladder that falls out of the notes is, cheapest first: JSON-Schema-validate inputs and outputs; static lint; dry-run read-only tools against recorded sample inputs and compare output shape to a golden run captured at approval; for consequential tools, no automatic live test, the first invocation is a human-approved live call whose result becomes the golden; and an idempotency probe only for tools the reviewer flags idempotent. Store a fingerprint of the DOM regions each tool touches (resolved `backendNodeId` presence plus a hash of the subtree text), recompute on load, and demote to "needs re-verification" on mismatch, then run the Builder to propose a patch. Subscribe to `WebMCP.toolsRemoved` for page-native tools disappearing. Test against the real Chromium runtime, never a mocked `modelContext`. Brittleness is broader than selectors: SSO sessions expire silently "so both the agent and user see a working screenshot as proof the session was alive, but only the next request redirects" ([DEV Community](https://dev.to/tinyfishie/when-web-agents-fail-debugging-goal-based-automation-307b)), so every tool needs a "session valid?" precheck, and tools should encode intent (role, text, ARIA, expected post-condition) rather than structure. One reassurance on anti-bot detection: 2026 fingerprinting research found agents like Claude for Chrome bypassed every evaluated anti-bot mechanism while "stealth and anti-detection mechanisms often increase detectability" ([arXiv 2606.30119](https://arxiv.org/abs/2606.30119)). Because Toolsmith runs inside the user's own logged-in session with their IP and fingerprint, it already sits in the least-detectable posture; do not add stealth.

## A saved tool cuts repeat-run cost by 95–100 percent

The economics rest on Anthropic's first-party list prices as of 2026-09-23: Opus 5 at **$5 / $25** per million tokens (cache read $0.50), Sonnet 5 at **$2 / $10** (cache read $0.20, the September price rise cancelled), Haiku 4.5 at **$1 / $5**, with cache reads at 0.1x base and the 5-minute write at 1.25x, so "caching pays off after one cache read" ([platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Anthropic's browser toolset `browser_toolset_20260801` "adds about 6,600 input tokens to a request," screenshots bill as image input, and accessibility trees and page text bill as ordinary input tokens; models from 4.7 onward tokenise roughly 30% heavier ([same page](https://platform.claude.com/docs/en/about-claude/pricing)). GPT-5.5's price appears on aggregators at $5 / $30 with 10% cached input, but openai.com was blocked and that figure is unverified ([morphllm](https://www.morphllm.com/openai-api-pricing)).

| Run type (10 model turns, accessibility-tree state) | Opus 5 | Sonnet 5 | Haiku 4.5 |
| --- | --- | --- | --- |
| Exploration, uncached (~60k in / 3k out) | ~$0.38 | ~$0.15 | ~$0.075 |
| Exploration, ~70% of input from cache | ~$0.19 | ~$0.07 | ~$0.035 |
| Second run via saved tool (~3k in / 200 out) | ~$0.02 | ~$0.008 | ~$0.004 |
| Second run, deterministic replay, no model | $0 | $0 | $0 |

These are the research note's arithmetic on the official prices, not measurements; a screenshot-driven exploration is plausibly 10–50x the token count and lands in the $1–$5 range on Opus 5, and a widely circulated practitioner estimate puts a multistep task at 20,000–60,000 tokens, roughly $0.10–$0.30 on a $5 frontier model ([dev.to](https://dev.to/leonting1010/your-ai-browser-agent-costs-3600month-heres-how-to-make-it-0-4228), snippet only). The shape of the table is the product argument: the first run is the expensive one, and everything after it is a cent or free. Two design consequences follow. The toolset definition and system prompt are byte-identical across turns and belong under a cache breakpoint, which is the largest lever on exploration cost. And the deterministic replay path (`workflow-use` claims replays run "with no LLM calls") should be a first-class mode, not an afterthought, because it is the only way the per-task number reaches zero ([workflow-use README](https://raw.githubusercontent.com/browser-use/workflow-use/main/README.md)). Publishing a measured cost and wall-clock table for exploration versus saved-tool runs on five to ten real sites would be more persuasive than any of the estimates above, and nobody in this category has published one.

## Spawn the unmodified CLI and never touch a token

Anthropic's position is written down and enforced. Its legal page states that OAuth "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications," that "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users," and that "developers may not collect, store, or intermediate Claude.ai credentials or session tokens" ([code.claude.com legal](https://code.claude.com/docs/en/legal-and-compliance)). The same page contains the carve-out Toolsmith must build on: nothing "prevent[s] an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code," provided the binary is unmodified, no authentication method is removed, and "each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential." A June 2026 help article confirms that "Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription's usage limits," because the separate-credit plan was paused on 2026-06-15 ([support.claude.com](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)).

Enforcement is real and recent. OpenCode removed subscription support at 1.3.0 after Anthropic asked ([opencode.ai](https://opencode.ai/docs/providers/)); pi users hit `400: You're out of extra usage` on 2026-09-21, with the reporter noting the same token succeeds under a generic system prompt and fails under pi's, which suggests fingerprinting by prompt ([earendil-works/pi #9838](https://github.com/earendil-works/pi/issues/9838)). The community workaround, `opencode-claude-auth`, reads Claude Code's OAuth token from the Keychain or `~/.claude/.credentials.json` and admits it "may stop working" ([griffinmartin/opencode-claude-auth](https://github.com/griffinmartin/opencode-claude-auth)); that is exactly the pattern the legal page forbids and a portfolio project must not touch. OpenAI has said nothing: in the Codex repo a maintainer pointed at the Terms of Use, declined to answer whether "Sign in with ChatGPT" from a third-party client is permitted, and follow-ups went unanswered through August 2026 ([openai/codex discussion #8338](https://github.com/openai/codex/discussions/8338)).

The safest design is therefore delegation, and it happens to be the cleanest architecture too. Toolsmith exposes its browser as an MCP server and spawns the user's already-installed, unmodified `claude` (interactive, `-p`, or via `@anthropic-ai/claude-agent-sdk`) and `codex` binaries as subprocesses; the user logs in through Anthropic's or OpenAI's own flow, and Toolsmith never sees a token. BYO API key is the first-class alternative, not a fallback, and the built-in agent should default to it. Do not embed any OAuth flow, do not read `.credentials.json`, and do not spoof a system prompt. Copy should say the product "runs Claude Code / Codex" in plain text and never put Claude or Anthropic in the name or logo, which the legal page also specifies. Two residual risks remain: the paused Agent SDK credit plan could return and cap subprocess usage, and "ordinary, individual usage" is enforced at Anthropic's discretion "without prior notice." Neither is avoidable; both are why the API-key path must be equally polished.

## For a laid-off senior frontend engineer, the portfolio case is strong if the demo is honest

The projects that broke out in 2025–26 shared a "magical moment" demo (Browser Use's founders credit their rise to delivering one fast), a benchmark number (Index's Show HN led with "92% on WebVoyager"), a tiny legible core (pi's four primitives and a sub-thousand-token system prompt), and public evals ([Open Source Startup Podcast](https://ossstartuppodcast.substack.com/p/episode-192-creating-browser-use); [HN 43773720](https://news.ycombinator.com/item?id=43773720); [mariozechner.at](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)). Hiring-side guidance for 2026 favours "2–4 standout projects" and four things that "reliably pass the skim: a tool you still use yourself months later, a merged pull request to a widely used open-source project, a teardown or measurement writeup ... and anything strangers have signed up for," and reviewers "trust portfolios that explain constraints, tradeoffs, bugs, and follow-up work" ([greatfrontend.com](https://www.greatfrontend.com/blog/frontend-developer-portfolio); [hakia.com](https://hakia.com/skills/building-portfolio/)).

Toolsmith maps onto that unusually well for a frontend engineer because the hard and novel parts are surface and systems judgment, not model research. The credibility artifacts are a 60–90 second demo of Builder mode creating, verifying, and re-running a tool from Claude Code; one honest cost and wall-clock table across real sites; a README that states the auth decision and what it cost; a test suite that replays saved tools against recorded fixtures; and evidence of daily personal use. The review UX is the place to show product thinking: the permission-comprehension literature says users do not understand permission names and that "interfaces that highlight data destinations rather than permission names have shown promise" ([Felt et al.](https://people.eecs.berkeley.edu/~daw/papers/perms-webapps11.pdf); [Island.io](https://www.island.io/education/browser-extension-security-defending-against-permissions-awareness-gaps)), so the reviewable unit should be the tool's contract and evidence (typed inputs and outputs, what it reads versus writes, where data goes, the recorded test call), with the TypeScript as the secondary view and a single end-to-end replay trace as the primary one, in the spirit of the "trace one path" order practitioners use for agent-written PRs ([PR Lens](https://prlens.dev/guides/how-to-review-copilot-coding-agent-pull-requests)). The bar for "noticed" is distorted by 100k-star outliers; a well-received Show HN and a handful of external users satisfies the "strangers signed up" category and is achievable. The engineering-interview story is equally good: an isolated-world sandbox for agent code, a hash-pinned version store, a DNS-rebinding-hardened local MCP server, and a Chromium feature flag driven through Electron's debugger are the kind of architecture decisions and tradeoffs an engineer interviewer wants to hear.

## Verdict: build it, position it as governance for the long tail, and design around four risks

Build it. The idea is sound under one framing and unsound under another, and the difference is entirely in positioning. The framing that survives every finding above is **"a local MCP server and tool workshop for sites without APIs, running in your own Chromium, on your own Claude Code / Codex subscription or API key."** The tagline is not "an agentic browser" and not "WebMCP for every site"; it is that Claude Code can call `toolsmith.github.search_issues` tomorrow at a cent a call, that you approved what that tool does, and that you can turn it off or roll it back without touching your agent. Native WebMCP consumption is what keeps it forward-compatible with Chrome 157 and Shopify; Builder mode is what keeps it useful on the 99% of sites that will never author tools; the governed lifecycle over a shared MCP server is what nobody else ships. Offer a CLI and skill surface alongside MCP, because Playwright's own docs now steer coding agents toward CLI plus skills on token grounds ([playwright.dev/mcp](https://playwright.dev/mcp/introduction)) and BrowserAct chose the same path.

| Risk | Why it matters | Design response |
| --- | --- | --- |
| WebMCP stalls or stays a Chromium niche (trial ends 2026-11-17, WebKit opposed) | If the standard is the thesis, the product dies with it | `document.modelContext` is one output target; the artifact is a typed tool with a schema, runnable via the polyfill, MCP, or deterministic replay |
| Generated code exfiltrates or acts inside a logged-in origin | Isolated worlds protect the heap, not the session; same-origin fetch carries cookies | Frozen `http()` helper, no network globals, static lint, app-assigned `consequential` default, SHA-256 approved-hash gate, isolated `session` partition, scheme blocking |
| Page-injected instructions steer consequential calls | Unhardened agents comply 16–86% of the time; no small app has probes or critics | Annotation-gated per-call approval, `untrustedContent` delimiting, a metadata-only critic call, a pinned current-model floor |
| Builder ROI vanishes at first-run parity | Budget-matched study: skill modules do not beat a plain actor on single tasks | Sell amortised reuse; ship deterministic replay; publish exploration-vs-replay cost and tool half-life |
| Subscription intermediation gets the product cut off | Anthropic enforces by prompt fingerprint; OpenAI is silent | Spawn unmodified `claude`/`codex`; BYO API key first-class; never read or store a token |
| Local MCP server reachable by DNS rebinding | Any site in the user's normal browser could hit it | Loopback bind, reject any `Origin`, bearer token in `safeStorage`, a 403 regression test |
| Chromium/WebMCP moves under Electron | `navigator` to `document` rename already broke mocked suites; one debugger per target | Feature-detect both names, idempotent attach, test on the real runtime, day-one spike on `WebMCP.enable` |

Sequence the work by risk retirement rather than by feature. Day one is the spike that nobody has published: does `WebMCP.enable` answer through `webContents.debugger` on Electron 44 with the Blink flag on? Week one is the shell, the debugger plumbing, the hardened MCP server, and consuming site-declared tools, all commodity. Weeks two through four are the versioned tool store with hashes and rollback, the review surface built around evidence rather than code, and the deterministic replay path. Only then does Builder mode start, because it is the open-ended part and it inherits every safety primitive built before it. Publish the cost table and a tool half-life the moment there are ten sites to measure. That order produces something demonstrable and defensible at every stage, which is what a portfolio needs, and it keeps the unbounded problem last, where it belongs.

## Conclusion

The most useful reframing from this research is that Toolsmith's scarce asset is not the browser, the agent or the standard, but the **approved, hashed, replayable tool as a unit of trust** that external agents inherit. The consumer vendors optimise for the opposite, fresh exploration every time on their own metered plans, and the developer tools that cache agent runs stop at "it worked once" with no human gate. That gap is small, technical, and unglamorous, which is why it is open, and it is exactly the kind of gap a single engineer with strong frontend and systems judgment can own before a funded team notices it is worth owning.

The second implication is that the project's credibility will come from numbers nobody has published rather than from features everybody has. A measured cost per task before and after a saved tool, and a measured half-life of generated tools on live sites, would be the first such figures in the category. Building the instrumentation to produce them is cheap, the write-up is the portfolio piece, and the results will tell you within a month whether the Builder loop earns its place or whether Toolsmith should narrow to the governed consumption of native tools and hand-approved recordings. Either outcome is a shippable product and a good story; only the un-instrumented version is neither.

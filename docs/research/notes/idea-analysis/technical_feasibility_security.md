## Key Question 1: Prompt injection against browser agents — documented attacks, published defenses, and what a small app can realistically implement

### Takeaway
Every major vendor (Anthropic, Google, OpenAI, Brave) treats indirect prompt injection as unsolved and defends with layers: model training, a classifier/critic that sees only untrusted content or only action metadata, origin scoping, and mandatory user confirmation for consequential actions. The only layers a small app can build are the deterministic ones (annotation-gated approval, origin allowlists, isolated profile, no free navigation), and benchmarks show those matter because unhardened agents follow injected instructions 16–86% of the time.

### Cited Findings

Documented attacks
- Brave (Aug 2025) showed Perplexity Comet fed webpage content to its LLM "without distinguishing between the user's instructions and untrusted content from the webpage"; a Reddit-post summary could let an attacker steal money or private data from signed-in accounts. — [Brave, Comet prompt injection (blocked; snippet only)](https://brave.com/blog/comet-prompt-injection/); corroborated by [Medianama summary (blocked; snippet only)](https://www.medianama.com/2025/10/223-prompt-injections-ai-browser/)
- Brave (21 Oct 2025) disclosed "unseeable" injections: faint text in images or screenshots is OCR'd and passed to the LLM "as if they were part of the user's query"; the same class hit the Fellou browser, and Brave frames it as "a systemic challenge facing the entire category of AI-powered browsers." — [Brave, Unseeable prompt injections (blocked; snippet only)](https://brave.com/blog/unseeable-prompt-injections/); [Futurism coverage](https://futurism.com/artificial-intelligence/researchers-severe-vulnerabilities-ai-browser-comet)
- Browser Use: `data:` and `blob:` URLs bypass the `allowed_domains` restriction, so "a prompt-injected LLM can trivially use data:text/html URLs to exfiltrate credentials, cookies, or page content to any external domain" even with an allowlist. — [browser-use/browser-use issue #4763](https://github.com/browser-use/browser-use/issues/4763)
- Academic WASP benchmark (built on WebArena; attacks restricted to attacker-controllable surfaces like GitLab/Reddit comments): agents begin executing the adversarial instruction 16–86% of the time but complete the attacker's goal only 0–17% of the time; the authors call this "security by incompetence." — [WASP paper (arXiv 2504.18575; abstract via search)](https://arxiv.org/pdf/2504.18575); [EmergentMind summary](https://www.emergentmind.com/topics/wasp-benchmark)
- WebMCP-specific attack paper (arXiv 2606.06387, 4 Jun 2026): "Mid-Session Tool Injection (MSTI)" via third-party scripts; two classes: Tool Hijacking (changing the tool set the agent sees via AbortSignal unregistration or registration race conditions) and Tool Framing (manipulating name, description, `readOnlyHint`, `inputSchema` to mislead the agent). — [arXiv 2606.06387 (blocked; abstract via search snippet)](https://arxiv.org/abs/2606.06387)

Published defenses and numbers — Anthropic (Claude in Chrome)
- Research preview, 25 Aug 2025: 123 test cases over 29 attack scenarios; autonomous-mode attack success rate (ASR) fell from 23.6% to 11.2% after mitigations; on four browser-specific vectors (hidden form fields, URL manipulation etc.) ASR fell from 35.7% to 0%. Mitigations: per-site permission grants users can revoke, confirmation "before taking high-risk actions like publishing, purchasing, or sharing personal data", blocked categories (financial services, adult, piracy), and classifiers for suspicious instruction patterns. Users were advised to avoid "sites that involve financial, legal, medical, or other types of sensitive information." — [Claude for Chrome announcement](https://claude.com/blog/claude-for-chrome)
- 24 Nov 2025: Opus 4.5 reached 1% ASR against an internal Best-of-N attacker; defense layers described as RL training on injected content, classifiers scanning "all untrusted content that enters the model's context window", and human red-teaming. No guidance for third-party developers is given. — [Anthropic, Mitigating the risk of prompt injections in browser use](https://www.anthropic.com/news/prompt-injection-defenses)
- GA, 26 Aug 2026: on a stronger red-teamer-sourced eval, attacks that reached the model succeeded 17.6% (Opus 4.5) vs 3.8% (Opus 5) with no safeguards; with "probes" (scanners over tool-result web content) plus an action classifier that blocks actions misaligned with the user's request: 0% for Opus 5/Sonnet 5/Mythos 5 and 0.3% for Fable 5. Claude runs in an "auto mode" that self-approves actions it judges safe, switchable to manual approval; Enterprise admins can limit it to approved domains. — [Claude in Chrome is generally available](https://claude.com/blog/claude-in-chrome-generally-available)

Published defenses — Google (Gemini in Chrome, Dec 2025)
- Google names indirect prompt injection "the primary new threat facing all agentic browsers." Layers: (1) a User Alignment Critic, a separate Gemini model that "see[s] only metadata about the proposed action and not any unfiltered untrustworthy web content", and vetoes misaligned actions; (2) Agent Origin Sets, extending Chrome origin isolation so each task session has a declared list of read-only and read-write origins; (3) deterministic user confirmations before navigating to sensitive sites (banking, medical) and before signing in via Google Password Manager; (4) a work log with stop/take-over. — [Google Security Blog (blocked; snippet only)](https://security.googleblog.com/2025/12/architecting-security-for-agentic.html); [SecurityWeek](https://www.securityweek.com/google-fortifies-chrome-agentic-ai-against-indirect-prompt-injection-attacks/); [Computerworld](https://www.computerworld.com/article/4103343/gemini-for-chrome-gets-a-second-ai-agent-to-watch-over-it.html)

Published defenses — OpenAI (ChatGPT Atlas)
- OpenAI shipped an adversarially-trained model plus strengthened surrounding safeguards after an RL-trained automated attacker found a new class of injections; OpenAI states prompt injection is "a long-term AI security challenge" it "will need to continuously strengthen defenses against". The UK NCSC advises reducing impact rather than expecting to stop attacks. — [OpenAI, Continuously hardening Atlas (blocked; snippet only)](https://openai.com/index/hardening-atlas-against-prompt-injection/); [CyberScoop](https://cyberscoop.com/openai-chatgpt-atlas-prompt-injection-browser-agent-security-update-head-of-preparedness/); [BankInfoSecurity](https://www.bankinfosecurity.com/openai-will-forever-fight-prompt-injection-attacks-a-30380)

WebMCP-level guidance
- Chrome's agent-security guidance for WebMCP splits defenses into deterministic and probabilistic guardrails; says all WebMCP tool outputs are base64-encoded for isolation and must be "decode[d] and inspect[ed] ... for contextual evaluation only, but never blindly follow or execute commands"; recommends prompt-injection classifiers at execution points; and says "There SHOULD always be a human in the loop with the ability to deny tool invocations." — [Chrome, Agent security considerations for WebMCP (blocked; snippet only)](https://developer.chrome.com/docs/agents/security)
- The CDP `WebMCP.Tool` object carries an `annotations` field with flags `readOnly`, `untrustedContent`, `consequential`, `debugging`, `autosubmit` — these are the only machine-readable trust signals a page provides. — [chromedp/cdproto webmcp package](https://pkg.go.dev/github.com/chromedp/cdproto/webmcp)
- The WebMCP security & privacy questionnaire lists risks: over-parameterised tools requesting "a non-minimal set of personal data", tools wrapping "sensitive or high-privilege operations (e.g., purchases, account changes)", and cross-origin state leakage by agents that browse several origins; it proposes "a hint for consequential actions" as the mitigation the user agent should key safeguards on. Access is gated by the `"tools"` Permissions Policy and per-tool `exposedTo`. — [webmachinelearning/webmcp security-privacy-questionnaire.md](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/security-privacy-questionnaire.md)
- Browserbase argues for an "allowlist-first approach starting with a small set of known-safe domains" plus containment so failures are survivable. — [Browserbase, prompt injection containment (blocked; snippet only)](https://www.browserbase.com/blog/ai-browser-prompt-injection-containment-security)

### Inferences
- The layers a small app cannot replicate are model-side (RL hardening, Anthropic's probes, Google's critic model, OpenAI's RL attacker). Toolsmith's realistic budget is the deterministic layer: (a) treat every tool without `readOnly` as requiring per-call approval, and hard-require approval when `consequential` is set; (b) when `untrustedContent` is set, wrap the output in a delimiter and a system note that it is data, mirroring Chrome's base64 isolation; (c) an origin allowlist that also blocks `data:`, `blob:`, `javascript:` and `file:` navigations (the Browser Use bypass shows a hostname allowlist is not enough); (d) a dedicated Electron `session` partition so the agent never touches the user's default cookies; (e) an action log with stop/take-over. A cheap "critic" call (a second LLM that sees only the tool name/args and the original user goal, never page content) is implementable with the Claude API and mirrors Google's metadata-only design.
- Toolsmith's Builder mode makes the tool-framing attack in arXiv 2606.06387 self-inflicted: the agent both reads page-supplied annotations and writes new ones. Agent-authored annotations must not be trusted for approval gating; the app should assign the trust class (default: consequential) regardless of what the generated code declares.
- Relying on the model's own robustness is reasonable only if Toolsmith uses a current Claude model; the 3.8% (Opus 5) vs 17.6% (Opus 4.5) unsafeguarded gap is a strong argument to pin a model floor.

### Gaps
- Could not fetch Brave's, Google's, or OpenAI's original posts; numbers and mechanisms above come from the vendors' own pages as reflected in search snippets and from secondary press. No OpenAI ASR numbers were found in any accessible source.
- AgentDojo per-model numbers were not retrievable (arXiv blocked); only WASP ranges are cited.
- The full text of arXiv 2606.06387 (attack success rates, proposed defenses) was not accessible; only the abstract's attack taxonomy is cited.

## Key Question 2: Agent-written code running in logged-in sites — threat model, what isolated worlds do and do not protect, sandboxing, and review/rollback prior art

### Takeaway
An isolated world protects the page's JS heap from the injected script and vice versa, but it shares the DOM and, critically, the origin — so generated tool code can read any rendered data, submit forms, and issue same-origin fetches with the user's cookies. Isolation is not a sandbox against exfiltration or CSRF-like actions; those need a CSP/network policy on the agent's world, a static allowlist of what generated code may call, hash-pinned versions, and human review before first live use.

### Cited Findings
- CDP `Page.addScriptToEvaluateOnNewDocument` with `worldName`: "creates an isolated world with the given name and evaluates given script in it"; a named world "shares the DOM but not the JavaScript heap." Left empty, the script runs in the page's main world. — [Crawlex, addScriptToEvaluateOnNewDocument trap](https://blog.crawlex.net/blog/cdp-add-script-evaluate-trap/)
- Electron: world ID 999 is the world used by `contextIsolation` (preload); ID 0 is the page's default world; Chrome extensions reserve `[1<<20, 1<<29)`. `executeJavaScriptInIsolatedWorld` exists on `webContents`; when script execution fails "the returned promise will not reject and the result would be undefined, because Chromium does not dispatch errors of isolated worlds to foreign worlds." — [electron PR #21190](https://github.com/electron/electron/pull/21190); [Electron webFrame docs mirror](https://fossies.org/linux/electron/docs/api/web-frame.md)
- The WebMCP spec notes tool `execute` callbacks are "ordinary JavaScript running in the registering document's existing realm" — invoking a tool is script execution inside the page. — [webmcp security-privacy-questionnaire.md](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/security-privacy-questionnaire.md)
- Browser Use's `allowed_domains` was bypassable through `data:`/`blob:` URLs, allowing exfiltration of "credentials, cookies, or page content to any external domain." — [browser-use issue #4763](https://github.com/browser-use/browser-use/issues/4763)
- MSTI/tool-hijacking research: injected scripts can unregister or re-register tools mid-session (AbortSignal, registration races) and mis-frame them via `readOnlyHint`/description. — [arXiv 2606.06387 (snippet only)](https://arxiv.org/abs/2606.06387)
- Stagehand (Browserbase) prior art for cached, self-healing automation: a successful atomic action "stores a cache entry that includes the selector and supporting metadata"; a later matching request replays "without calling an LLM"; when a cached selector fails, `selfHeal` "triggers a fresh LLM inference to find the new element and updates the cache automatically." — [Browserbase, How caching works in Stagehand (blocked; snippet only)](https://www.browserbase.com/blog/stagehand-caching); [browserbase/stagehand README (v4)](https://github.com/browserbase/stagehand)
- WebMCP's Chrome DevTools panel logs "registration, schema validation, and invocation history" (Chrome 149+), i.e. the browser itself treats tool registration/invocation as auditable events. — [Chrome DevTools WebMCP docs (blocked; snippet only)](https://developer.chrome.com/docs/devtools/application/webmcp)

### Inferences
- Threat model for Builder-mode code (all consequences follow from "same origin, shared DOM"):
  - Exfiltration: generated code can `fetch()` anywhere the page's CSP allows and can read DOM text, `localStorage` of the origin, and form values. Isolated worlds do not restrict network access; a named world created by CDP is still subject to the page's CSP `connect-src`, but many sites have permissive or no CSP.
  - CSRF-like actions: the code can submit forms and call the site's own XHR endpoints with the user's cookies; no CSRF token protects against same-origin script.
  - Session theft: `document.cookie` is readable for non-HttpOnly cookies from any world sharing the document; HttpOnly cookies are not readable but are still sent on same-origin requests the code makes.
  - Tool shadowing (self-inflicted MSTI): a Toolsmith-registered tool can shadow a page-native one by name; the app must namespace generated tools (e.g. `toolsmith.<site>.<name>`) and never let an injected tool replace a page-registered one.
- What isolated worlds do buy: the page cannot tamper with Toolsmith's helper objects or override `document.modelContext` methods the injected code relies on (heap separation), and the injected code cannot be trivially detected/blocked by page scripts monkey-patching prototypes. That protects integrity of the injection, not confidentiality of the user's session.
- Sandboxing generated tool code (mitigations ranked by cost): (1) Do not give generated code `fetch`/`XMLHttpRequest`/`WebSocket`/`navigator.sendBeacon`; expose a Toolsmith-owned `http()` helper that enforces a same-origin-only (or per-tool allowlisted) policy and logs every request. Since the world shares no heap with the page, the helper can be sealed with `Object.freeze` before the generated function is evaluated. (2) Static lint of generated source for banned globals (`eval`, `Function`, `import()`, `document.cookie`, `localStorage`, network APIs) before it is ever injected. (3) Run each generated tool with an AbortSignal timeout and a max-invocations-per-minute cap. (4) Mark every generated tool `consequential` unless a human reviewer flips it to `readOnly` after reading the code — never trust the agent's own annotation. (5) Content-hash (SHA-256) the injected bundle; store `{hash, source, version, verified_at, approved_by}`; refuse to inject any source whose hash is not in the approved set; keep N prior versions for one-click rollback (Stagehand's cache-then-heal loop is the closest shipped analogue, but Toolsmith needs an explicit human approval gate that Stagehand does not have).
- `Page.addScriptToEvaluateOnNewDocument` has no frame filter: the world is created in every frame of every document, including cross-origin iframes (ads, embedded widgets). Toolsmith should check `frameId`/origin at the top of the injected script and no-op outside the target origin, or route injection through `Page.createIsolatedWorld` per target frame.

### Gaps
- No published prior art was found for a "human reviews generated browser-tool code, hashes it, and can roll back" UX; the closest analogues are Stagehand's action cache and OWASP's MCP tool-poisoning guidance (page blocked, not cited). This should be treated as novel product work.
- Whether a CDP-created isolated world inherits the page's CSP for `connect-src` in Chromium 152 was not verified from source; treat "CSP applies" as an assumption to test.

## Key Question 3: Electron specifics — WebMCP CDP domain reachability, origin trials vs feature flags, addScriptToEvaluateOnNewDocument reliability, debugger conflicts, performance, DevTools banner

### Takeaway
Electron 44 ships Chromium 152.0.7977.54, which is inside Chrome's WebMCP origin-trial window (149–156) and later than the Chrome 149 DevTools WebMCP panel, so the `WebMCP` CDP domain almost certainly exists in the binary — but no report of anyone driving it from `webContents.debugger` was found, and the feature must be switched on by a Blink runtime flag rather than an origin-trial token. The hard constraints are documented: one debugger client per target (opening DevTools detaches you), and `sendCommand` may hang until navigation.

### Cited Findings

Versions and status
- Electron 44.0.0 (released 25 Aug 2026 per search; the release page returned an obviously wrong "2024" date in extraction — treat exact day as unverified) ships Chromium 152.0.7977.54, Node v24.18.1, V8 15.2; requires macOS 13+; 32-bit builds removed. — [electron v44.0.0 release](https://github.com/electron/electron/releases/tag/v44.0.0); [Electron 44 blog (snippet only)](https://www.electronjs.org/blog/electron-44-0)
- Electron 46 removed the synchronous `safeStorage` API (`isEncryptionAvailable`, `encryptString`, `decryptString`); async variants remain and can decrypt older data. — [electron docs/api/safe-storage.md](https://raw.githubusercontent.com/electron/electron/main/docs/api/safe-storage.md)
- WebMCP in Chromium: developer-testing flag `chrome://flags/#enable-webmcp-testing` ("WebMCP for testing") from Chrome 146.0.7672.0; origin trial live in Chrome 149 (and Edge 150); trial runs Chrome 149 through 156 (snippet); Chrome moved the API from `navigator.modelContext` to `document.modelContext` (deprecated alias in 150, removed in 153; Chrome 152+ puts it on `document`); Chrome 153 carries `blink::ModelContext`, `kWebMCP`, `kWebMCPTesting`, and `InspectorWebMCPAgent`. The spec is a W3C WebML CG Draft Report last updated 28 Jul 2026 and "not yet a stable web platform feature." — [webmcp implementation-status.md](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/implementation-status.md); [Bug0, WebMCP in Chrome 146](https://bug0.com/blog/webmcp-chrome-146-guide); [ModelPiper, API migration](https://modelpiper.com/blog/webmcp-chrome-api-migration-mocked-tests); [Spronta, State of WebMCP July 2026](https://www.spronta.com/blog/state-of-webmcp-july-2026/)
- CDP `WebMCP` domain: commands `enable` (fires `toolsAdded` for all current tools), `disable`, `invokeTool(frameId, toolName, input) -> invocationId`, `cancelInvocation(invocationId)`; events `toolsAdded`, `toolsRemoved`, `toolInvoked`, `toolResponded` (status Completed/Canceled/Error, output, errorText, exception); `Tool` has `name, description, inputSchema, annotations, frameId, backendNodeId, stackTrace`. — [chromedp/cdproto webmcp](https://pkg.go.dev/github.com/chromedp/cdproto/webmcp); [Scrapfly CDP reference: WebMCP](https://scrapfly.io/docs/cloud-browser-api/cdp-reference/WebMCP)
- Chrome DevTools has a WebMCP panel (under Application) as of Chrome 149. — [Chrome DevTools WebMCP docs (blocked; snippet only)](https://developer.chrome.com/docs/devtools/application/webmcp)

Origin trials in Electron
- Chrome's own guidance: origin-trial tokens "should not be relied upon to enable trial features in other browsers, including Chromium and other Chromium-based browsers"; a token yields `NotSupported` when "the origin trial defined by the token is not supported in the Chromium embedder", where an embedder "can be a browser (such as Chrome or Edge), a WebView, or some other user agent." — [Chrome origin-trial troubleshooting (blocked; snippet only)](https://developer.chrome.com/docs/web-platform/origin-trial-troubleshooting); [Chromium origin_trials_integration.md](https://chromium.googlesource.com/chromium/src/+/master/docs/origin_trials_integration.md)
- Chromium runtime-enabled features can be switched on by `--enable-blink-features=<Name>` or `--enable-experimental-web-platform-features`, and base::Features by `--enable-features=`. — [Chromium RuntimeEnabledFeatures.md](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/platform/RuntimeEnabledFeatures.md)
- Electron warns that `enableBlinkFeatures` "exposes users to some security risk" and should never be enabled speculatively. — [Electron security tutorial (snippet only)](https://www.electronjs.org/docs/latest/tutorial/security)

Debugger behaviour
- `webContents.debugger.attach([protocolVersion])`; `detach` event fires "when `webContents` is closed or DevTools is invoked for the attached `webContents`"; `sendCommand(method[, commandParams, sessionId])`; if called before target navigation the promise "may not resolve until navigation occurs"; empty results resolve `{}`. — [electron docs/api/debugger.md](https://raw.githubusercontent.com/electron/electron/main/docs/api/debugger.md)
- Historical error "DevTools connection failed when another debugger is already attached to this target" (Electron 1.4.x) — Electron does not support two simultaneous debugger clients on one target; pick remote debugging or DevTools, not both. — [electron issue #8336](https://github.com/electron/electron/issues/8336)
- Using CDP `Fetch` via `webContents.debugger` with auto-attached targets stopped working in 11.x and crashed 12.x — evidence that less-common domains/target combinations through the Electron transport can regress across majors. — [electron issue #27768](https://github.com/electron/electron/issues/27768)
- Electron 44 fixed "missing DevTools Network panel requests after navigation" and a crash "when closing DevTools while host WebContents destroyed". — [electron v44.0.0 release](https://github.com/electron/electron/releases/tag/v44.0.0)

Injection reliability
- `Page.addScriptToEvaluateOnNewDocument` runs "in every frame upon creation (before loading frame's scripts)"; it has no frame filter, so with `worldName` Chrome "would create the world in every frame of every document." — [microlinkhq/browserless PR #926](https://github.com/microlinkhq/browserless/pull/926); [Crawlex](https://blog.crawlex.net/blog/cdp-add-script-evaluate-trap/)
- Puppeteer pairs `Page.addScriptToEvaluateOnNewDocument` with `Page.createIsolatedWorld` using the same `worldName`, and had to stop reusing a stale utility world. — [puppeteer PR #6528](https://github.com/puppeteer/puppeteer/pull/6528/files)
- Known driver bug class: a child iframe navigation invalidates the main frame's cached `executionContextId` for drivers using isolated worlds. — [lightpanda issue #2400](https://github.com/lightpanda-io/browser/issues/2400)
- Detection: sites that fingerprint automation look for CDP-created worlds and `Runtime.enable` side effects; Toolsmith's injection is visible to anti-bot systems. — [Crawlex, Runtime.enable leak](https://blog.crawlex.net/blog/detecting-cdp-runtime-enable/); [Foil, CDP detection 2026](https://usefoil.com/learn/cdp-detection)

Performance
- CDP domains are independent; enabling only what you need reduces overhead; the `DOM` domain is "computationally heavy and memory-intensive" because it maintains rich debugging metadata, which is why Puppeteer/Playwright prefer `Runtime.evaluate`. Overhead mostly comes from breakpoints and frequent `Runtime.evaluate` calls freezing the event loop. — [Lightpanda, CDP under the hood](https://lightpanda.io/blog/posts/cdp-under-the-hood); [Medium, CDP in Selenium 4](https://medium.com/@nitish.d599/mastering-chrome-devtools-protocol-cdp-in-selenium-4-a-practical-guide-for-test-automation-16d9227431fc)

Banner
- Chrome adds an infobar "whenever it is controlled in an automated fashion", which changes the CSS viewport height. — [Electron automated-testing tutorial (snippet only)](https://www.electronjs.org/docs/latest/tutorial/automated-testing); [playwright issue #36238](https://github.com/microsoft/playwright/issues/36238)

### Inferences
- Reachability: `webContents.debugger` is a generic CDP transport, and Chromium 152 > 149 (DevTools panel) so `WebMCP.enable` should be accepted once the Blink feature is on. This is unverified — nobody has published a test. It is a one-day spike: `app.commandLine.appendSwitch('enable-blink-features', 'WebMCP')` (exact runtime-feature name to be confirmed against `runtime_enabled_features.json5` for 152; search evidence names `kWebMCP`/`kWebMCPTesting`, and the `#enable-webmcp-testing` flag maps to a feature that also enables `WebMCP`), attach, `WebMCP.enable`, load a page that calls `document.modelContext.registerTool`, and expect `toolsAdded`.
- Origin-trial tokens are the wrong lever for Electron: token validation is embedder-policy-driven, Chrome documents that tokens are not guaranteed outside Chrome, and Toolsmith embeds arbitrary third-party sites whose tokens (if any) are scoped to their own origins. Enabling the runtime feature by command-line switch is the only approach that works for every embedded site; accept Electron's `enableBlinkFeatures`-style security warning and document why.
- One debugger client per target means Toolsmith cannot offer "open DevTools on this view" while its agent is attached without losing `WebMCP.enable`, `Page.addScriptToEvaluateOnNewDocument` registrations, and all state. Handle `detach` by re-attaching and re-registering everything (idempotent setup routine), and disable the DevTools menu item for agent-attached views.
- Because `addScriptToEvaluateOnNewDocument` fires in every frame, the injected bootstrap must self-gate on `location.origin` and only register tools in the top frame of the target origin; otherwise Toolsmith will register tools inside cross-origin iframes (and leak tool descriptions to them).
- Performance: keeping the debugger attached with only `WebMCP`, `Page` and `Runtime` enabled should be cheap; avoid `DOM.enable` and avoid `Network.enable` on every view. The measurable costs in the cited sources come from breakpoints and heavy evaluate loops, not from being attached.
- The "controlled by automated test software" infobar belongs to Chrome's `chrome/` UI layer that Electron does not ship; Electron's `WebContentsView` has no infobar surface, so no banner is expected. Unverified — confirm in the same spike.

### Gaps
- No Electron issue, PR, or blog post was found that mentions the WebMCP CDP domain at all; reachability from `webContents.debugger` is inferred, not demonstrated.
- The exact Blink runtime-feature name(s) for WebMCP in Chromium 152 were not confirmed from `runtime_enabled_features.json5` (chromium source fetch not attempted after repeated proxy blocks).
- Whether the CDP `WebMCP` domain is marked `experimental` in `browser_protocol.pdl` could not be verified (chromedevtools.github.io blocked; cdproto rendering showed no marker).
- No measured numbers for the overhead of an always-attached debugger in Electron were found.

## Key Question 4: Verification of generated tools and drift detection

### Takeaway
Shipped systems (Stagehand) verify by "run it, and if it fails, re-plan with the LLM and rewrite the cache"; nobody publishes a stronger proof of tool correctness. For Toolsmith the practical bar is schema validation + a recorded golden run per version + read-only dry-runs before any consequential live call + a page fingerprint that triggers re-verification when the site changes.

### Cited Findings
- Stagehand cache entries hold "the selector and supporting metadata"; on a hit the SDK "executes using the cached selector without calling an LLM"; on failure `selfHeal` re-infers and updates the cache; a page fingerprint mismatch (site redesign) falls back to AI. — [Browserbase caching blog (blocked; snippet only)](https://www.browserbase.com/blog/stagehand-caching); [Stagehand caching docs (blocked; snippet only)](https://docs.stagehand.dev/examples/caching); [stagehand README](https://github.com/browserbase/stagehand)
- Stagehand v4 README: `act()`, `observe()`, `extract()` "refresh how an action happens when the site changes underneath it"; server-side `cache: true` returns identical calls "no tokens spent." — [browserbase/stagehand](https://github.com/browserbase/stagehand)
- CDP `WebMCP.toolResponded` reports `status` (Completed/Canceled/Error), `output`, `errorText` and an optional `exception`, and `Tool` includes `inputSchema` and `stackTrace` — enough to machine-check a tool call against its declared schema and attribute the registration to a script. — [chromedp/cdproto webmcp](https://pkg.go.dev/github.com/chromedp/cdproto/webmcp)
- Chrome DevTools' WebMCP panel does "schema validation" on registration and keeps "invocation history." — [Chrome DevTools WebMCP docs (blocked; snippet only)](https://developer.chrome.com/docs/devtools/application/webmcp)
- A tool-registration test that mocks `document.modelContext` can pass while registering nothing in real Chrome ("Eight WebMCP tools that registered nothing"), because of the `navigator` -> `document` migration. — [ModelPiper](https://modelpiper.com/blog/webmcp-chrome-api-migration-mocked-tests)

### Inferences
- Verification ladder for a generated tool, cheapest first: (1) JSON-Schema-validate `inputSchema`/outputs and reject tools whose `execute` is not a function; (2) static lint for banned APIs (see Q2); (3) dry-run: for tools the human has marked read-only, invoke with recorded sample inputs and compare output shape against a golden run captured at approval time; (4) for consequential tools, no automatic live test — the first invocation is a human-approved live call whose result is recorded as the golden; (5) idempotency probe only for tools the reviewer flags idempotent (call twice, diff page state via a DOM snapshot hash).
- Drift: store a per-tool fingerprint of the DOM regions the tool touches (selectors resolved to `backendNodeId` presence + a hash of the relevant subtree text). On each page load, recompute; a mismatch demotes the tool to "needs re-verification" and blocks auto-approval, then runs the Builder loop to propose a patch that the human reviews (Stagehand's self-heal, but gated). Also subscribe to `WebMCP.toolsRemoved` to detect page-native tools disappearing.
- Test against the real Chromium runtime, never a mocked `modelContext` (ModelPiper's failure mode), and feature-detect `document.modelContext || navigator.modelContext` since Chromium 152 sits on the boundary of the alias removal.

### Gaps
- No academic or industry benchmark of generated-tool correctness or drift rates was found; no source gives failure rates for cached actions after site changes.
- Stagehand's exact fingerprint algorithm is not documented in any accessible source.

## Key Question 5: Local MCP server hardening — DNS rebinding, SDK option names, token storage

### Takeaway
The MCP spec makes Origin validation mandatory and localhost binding recommended; the official TypeScript SDK exposes `enableDnsRebindingProtection`, `allowedHosts` and `allowedOrigins` on `StreamableHTTPServerTransport` (v1) and auto-arms them in `createMcpExpressApp` for loopback binds (v2), with a known gap for non-loopback hosts. Store the bearer token with Electron's async `safeStorage` API, which on macOS keys to the app's Keychain entry and needs a code-signed build.

### Cited Findings
- Spec (2025-06-18 transports): servers "MUST validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks"; "When running locally, servers SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)"; "SHOULD implement proper authentication for all connections"; `Mcp-Session-Id` "SHOULD be globally unique and cryptographically secure"; clients send HTTP DELETE to end sessions. — [modelcontextprotocol spec, transports.mdx](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-06-18/basic/transports.mdx)
- TypeScript SDK v1 option names: `new StreamableHTTPServerTransport({ sessionIdGenerator, enableDnsRebindingProtection: true, allowedHosts: ['127.0.0.1', ...], allowedOrigins: [...] })`; protection is "disabled by default for backwards compatibility." — [typescript-sdk docs/server.md (search snippet; the raw path 404s on main, page exists on github.com)](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/server.md)
- SDK v2 (implements the 2026-07-28 MCP spec; packages `@modelcontextprotocol/express`, `@modelcontextprotocol/node`): `createMcpExpressApp({ host, allowedHosts, allowedOrigins })` auto-arms Host and Origin validation for loopback binds (127.0.0.1/localhost); binding to `0.0.0.0` requires an `allowedHosts` list; an explicit `allowedOrigins` replaces the default localhost allowlist; requests without an Origin header pass; a present, disallowed or unparseable Origin gets 403; "If you use `NodeStreamableHTTPServerTransport` directly with your own HTTP framework, you must implement Host header validation yourself." — [typescript-sdk README (v2)](https://github.com/modelcontextprotocol/typescript-sdk); [SDK v2 Server Guide (snippet)](https://ts.sdk.modelcontextprotocol.io/v2/documents/Documents.Server_Guide.html)
- Open SDK issue #2843: `createMcpExpressApp`/`createMcpHonoApp` silently skip Host/Origin middleware for non-loopback hosts other than `0.0.0.0`/`::` (LAN IP, container hostname) with no warning. Companion issue #2844: `createMcpHandler` is validation-free. — [typescript-sdk issue #2843](https://github.com/modelcontextprotocol/typescript-sdk/issues/2843); [issue #2844](https://github.com/modelcontextprotocol/typescript-sdk/issues/2844)
- Real-world miss: Backstage's MCP streamable-HTTP endpoint shipped with no DNS-rebinding protection. — [backstage issue #35791](https://github.com/backstage/backstage/issues/35791)
- Electron `safeStorage`: macOS "encryption keys are stored for your app in Keychain Access in a way that prevents other applications from loading them without user override"; the app "should be code signed" or "macOS may not recognize different builds of your app as the same application"; Windows DPAPI protects against other users but not other apps in the same session; Linux falls back to `basic_text` when no secret store exists. Async API: `isAsyncEncryptionAvailable()`, `encryptStringAsync()`, `decryptStringAsync()` returning `{ result, shouldReEncrypt }` (key rotation). Sync API removed in Electron 46. — [electron docs/api/safe-storage.md](https://raw.githubusercontent.com/electron/electron/main/docs/api/safe-storage.md)
- `safeStorage` on macOS can trigger a Keychain password prompt after an Electron upgrade (signing identity change). — [electron issue #43233](https://github.com/electron/electron/issues/43233)
- Independent analysis reports `safeStorage` uses AES-128-CBC with a hardcoded IV, keyed from the OS store — i.e. the OS keychain, not the cipher, is the security boundary. — [Gerald Chen, Cracking open Electron safeStorage](https://chenguangliang.com/en/posts/blog169_electron-credential-storage-security/)

### Inferences
- Concrete config for Toolsmith: bind `127.0.0.1` only; `allowedHosts: ['127.0.0.1:<port>', 'localhost:<port>']`; `allowedOrigins: []` plus reject any request that carries an Origin header at all (Claude Code/Codex/Cursor are not browsers and send none — the SDK already passes Origin-less requests); require `Authorization: Bearer <token>` on every request including `initialize`, compare with constant-time equality, and rotate the token per app launch or on user request; generate the token with `crypto.randomBytes(32)` and persist only the `safeStorage`-encrypted blob under `app.getPath('userData')`. Because the app is on Electron 44, use the async `safeStorage` API now so the Electron 46 removal is a no-op.
- Sign and notarize the macOS build before relying on `safeStorage`; unsigned dev builds will both prompt and possibly lose access to previously encrypted tokens.
- Add an integration test that sends a request with `Host: evil.example` and one with `Origin: https://evil.example` and asserts 403, so an SDK upgrade cannot silently disarm the check (issue #2843 shows the arming rules are subtle).

### Gaps
- The v2 SDK's exact transport option names (`hostHeaderValidation`/`originValidation` or otherwise) could not be read verbatim because both docs pages returned 404 through the proxy; only `createMcpExpressApp({ allowedHosts, allowedOrigins })` and the v1 `enableDnsRebindingProtection` names are confirmed by sources.
- Whether the 2026-07-28 spec revision changed the Origin/DNS-rebinding wording was not checked (only the 2025-06-18 file was fetched).

## Key Question 6: Effort estimate — commodity vs hard

### Takeaway
The shell, CDP plumbing, and local MCP server are commodity; the Builder loop's code quality, safe sandboxing of generated code, and drift-aware verification are the genuinely hard, unbounded parts and carry the security risk.

### Cited Findings
- Electron 44 provides `WebContentsView`, `webContents.debugger` (CDP transport), `safeStorage`, and `session` partitions out of the box. — [electron v44.0.0 release](https://github.com/electron/electron/releases/tag/v44.0.0); [electron docs/api/debugger.md](https://raw.githubusercontent.com/electron/electron/main/docs/api/debugger.md)
- The MCP TypeScript SDK v2 ships Express/Node HTTP integrations with built-in host/origin checks. — [typescript-sdk](https://github.com/modelcontextprotocol/typescript-sdk)
- Existing packages already bridge WebMCP tools to MCP clients via Chrome DevTools (`@mcp-b/chrome-devtools-mcp`, WebMCP-org `chrome-devtools-mcp`), showing the read/invoke path is a known pattern. — [WebMCP-org/npm-packages chrome-devtools-mcp](https://github.com/WebMCP-org/npm-packages/tree/main/packages/chrome-devtools-mcp); [npm @mcp-b/chrome-devtools-mcp](https://www.npmjs.com/package/@mcp-b/chrome-devtools-mcp)
- WebMCP is an origin-trial, non-stable API with an in-flight `navigator`->`document` migration and a 149–156 trial window, so the platform under Toolsmith will keep moving. — [webmcp implementation-status.md](https://raw.githubusercontent.com/webmachinelearning/webmcp/main/implementation-status.md); [ModelPiper](https://modelpiper.com/blog/webmcp-chrome-api-migration-mocked-tests)
- Every vendor states prompt injection cannot be fully eliminated; defenses are continuous. — [Anthropic GA post](https://claude.com/blog/claude-in-chrome-generally-available); [BankInfoSecurity on OpenAI](https://www.bankinfosecurity.com/openai-will-forever-fight-prompt-injection-attacks-a-30380)

### Inferences (no direct source; estimate)
- Commodity (days to ~2 weeks): Electron shell with `WebContentsView` tabs and an isolated `session` partition; attach/reattach debugger; `WebMCP.enable`/`invokeTool` bridge; MCP server over `createMcpExpressApp` with bearer auth; `safeStorage`-backed token; per-call approval dialog keyed on annotations; origin allowlist with scheme blocking.
- Medium (weeks): Page fingerprinting + drift demotion; versioned tool store with hashes and rollback; audit log UI; a metadata-only "critic" LLM pass before consequential calls; feature-flag handling across Chromium 152/153 (`navigator` vs `document` alias).
- Hard / open-ended: Builder loop quality (getting an LLM to write tools that survive real SPAs, auth flows, and anti-bot detection of CDP worlds); a defensible sandbox for generated code (frozen helper API, static lint, network policy) that still lets useful tools work; verification of consequential tools without side effects; keeping ASR low without vendor-scale probes/critics. Expect this to dominate the schedule and to require ongoing maintenance as the WebMCP API and Chromium move.
- Highest-severity residual risks, in order: (1) agent-written code exfiltrating session data from a logged-in site (Q2); (2) page-injected instructions steering the agent into consequential tool calls (Q1); (3) a mis-configured local MCP server reachable via DNS rebinding from any website the user visits in their normal browser (Q5); (4) platform breakage when Chromium/WebMCP changes under Electron (Q3).

### Gaps
- No public effort/cost data exists for a product of this shape; the estimates above are inferences from component maturity, not sourced figures.

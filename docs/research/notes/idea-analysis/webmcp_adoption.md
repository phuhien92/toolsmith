## Key Question 1: Which named production sites/companies have shipped WebMCP tools, and roughly how many?

### Takeaway
Two very different numbers are both true: measured organic adoption on the open web was zero of ~111k top domains in May 2026 (pre-trial), while by late August 2026 Shopify auto-enabled WebMCP tools on every Liquid storefront ("millions" of stores) with no merchant action, and OpenAI/Google name roughly ten large brands as origin-trial participants. ## Key Question 3: Mozilla and Apple/WebKit standards positions

### Takeaway
WebKit formally opposes (issue #670, closed with "position: oppose") on the grounds that "a parallel agent-facing tool layer" is not the right solution and the proposal comes "before the actual problem has been established"; Mozilla is "neutral" (issue #1412), meaning not convinced of the merits but seeing no significant harm. Neither has an implementation timeline, so WebMCP is a Chromium-only capability for the foreseeable future.

### Cited Findings
- WebKit #670 opened 2026-05-28; closed with label "position: oppose"; concern labels visible: API design ("error-prone, poorly named, or inconsistent"), duplication of existing web platform functionality, internationalization, portability, privacy, security, unclear use cases — [WebKit/standards-positions#670](https://github.com/WebKit/standards-positions/issues/670). Quoted statements: 2026-06-03 "we do not think a parallel agent-facing tool layer is the right solution"; 2026-06-17 WebMCP "proposes a new solution before the actual problem has been established" (snippets, comments API returned 403) — [Wildernessone tracker PR #152](https://github.com/Wildernessone/agent-interface-v2/pull/152); [dev.to: WebKit opposes WebMCP](https://dev.to/r0bertini/webkit-opposes-webmcp-heres-what-to-actually-build-today-18dn).
- Mozilla #1412 opened 2026-05-28; closed with "position: neutral"; snippets disagree on the date (neutral "landed" 2026-06-01 vs issue "closed on 2026-08-05"); Mozilla's definition of neutral: "not convinced of the merits of this work, but does not see any significant negative potential" — [mozilla/standards-positions#1412](https://github.com/mozilla/standards-positions/issues/1412); [Mozilla positions index](https://mozilla.github.io/standards-positions/).
- The position requests describe two use cases: built-in browser agents ("Gemini in the sidebar in Chrome, ChatGPT Atlas, Co-pilot in Edge") and in-page JS agents "possibly in cross-origin iframes"; "WebMCP was conceived with only the first use case in mind" and expanded on developer demand — [WebKit #670 body](https://github.com/WebKit/standards-positions/issues/670).
- Standards status: "WebMCP is not a W3C Standard nor is it on the W3C Standards Track"; Community Group Draft dated 2026-02-12, editors Walderman (Microsoft), Sagar (Google), Farolino (Google); the CG charter lists "WebMCP API" as a deliverable "for web apps to expose their functionality as tools to AI agents and assistive technologies" (snippets) — [spec](https://webmachinelearning.github.io/webmcp/); [CG charter](https://webmachinelearning.github.io/charter/). No Working Group charter item for WebMCP found in the WebML WG charter — [WG charter](https://www.w3.org/2023/04/web-machine-learning-charter.html).
- Cross-origin exposure remains contested in the issue tracker: "The unresolved question is not whether a page's own agent can call its own tools; it's who else can: a cross-origin iframe, an opener or popup window, the browser's own built-in agent watching another tab" (snippet) — [Zylos Research 2026-07-31](https://zylos.ai/research/2026-07-31-browser-native-agent-tool-exposure-consent-model/).

### Inferences
- With WebKit opposed, Safari/iOS will not expose `document.modelContext`; any product depending on WebMCP is Chromium-desktop-first (plus ChatGPT's embedded browser). Mozilla neutral leaves a door open but signals no near-term Firefox implementation.
- Two engines' concerns overlap with developer criticism (duplication of the accessibility tree, undefined consent/security model), so those are the issues most likely to shape or stall a standards-track move.

- Could not read the actual Mozilla/WebKit staff comments (GitHub API 403, HTML fetch showed labels only); the WebKit quotes are from secondary trackers and should be verified before quoting publicly.
- The Mozilla decision date is inconsistent across sources (June 1 vs August 5, 2026).

## Key Question 4: Developer sentiment and main criticisms

### Takeaway
Sentiment is split: web-standards and agent-tooling people (Heilmann, Builder.io, MCP-B, Arcade) are enthusiastic about "tools, not DOM" and ~90% token savings; skeptics on HN and in essays argue it is a second interface that drifts from the UI, that server-side MCP or plain APIs dominate for anyone willing to invest, that the security/consent model is undefined, and that vendors are already "selling security tooling for a threat model that doesn't yet exist".

### Cited Findings
- HN threads (all blocked; titles and dates from search): "WebMCP" (item 45622604, ~Oct 2025), "Show HN: Using WebMCP to make the CDP MCP server 90% more token efficient" (46223714), "Chrome Announced WebMCP Integration" (46969572, ~Feb 2026), "WebMCP Proposal" (47037501), "Ask HN: What Is the Point of WebMCP?" (47085076, ~Feb 2026), "WebMCP is available for early preview" (47211249), "WebMCP: Teaching Your Website to Talk to AI Agents" (49450417, Sep 2026), "WebMCP Challenge – OpenAI" (49455713, Sep 2026) — [HN search](https://news.ycombinator.com/item?id=47085076).
- Representative HN criticism (snippet from thread 49450417): "I have no idea who at Google is advocating for this, but it's a half-baked idea that goes against 20 years of web standard work"; skeptics "question whether website owners should be asked to maintain yet another interface format"; proponents point to "the 90% token reduction and the end of fragile screen-scraping" — [Frase summary](https://www.frase.io/blog/what-is-webmcp); [HN 49450417](https://news.ycombinator.com/item?id=49450417).
- "Why not an API / server-side MCP": "WebMCP occupies the worst of both worlds: it demands developer effort like server-side MCP but routes through the browser, creating a second-class copy that drifts from the UI"; "the tool contract must stay in sync with every UI change indefinitely, and the failure mode is silent drift"; "it sits in the gap between 'willing to invest' and 'won't invest,' and history says that gap is empty" (snippets) — [The WebMCP False Economy](https://manveerc.substack.com/p/webmcp-false-economy-server-side-mcp-browser-apis).
- Defence of the browser locus: unique capabilities an HTTP API lacks, e.g. `getCurrentPage` and `navigate` because "an HTTP API has no idea what you are looking at"; the agent "uses the shopper's live browser session" so cart and auth state are shared (snippets) — [agentrq](https://agentrq.com/blog/webmcp-browser-agents); [Builder.io: Everyone's Missing the Point of WebMCP](https://www.builder.io/blog/webmcp).
- Accessibility-tree redundancy is a tracked spec issue: "Redundancy with the accessibility tree" #91 — [webmcp#91](https://github.com/webmachinelearning/webmcp/issues/91); W3C AI-accessibility discussion — [w3c/ai-accessibility#26](https://github.com/w3c/ai-accessibility/issues/26).
- Prompt injection is a tracked spec issue (#11) and Chrome's own guidance concedes "Prompt injection in LLMs appears to be a largely unsolved issue" and names two WebMCP vectors: "malicious manifests with hidden instructions in tool definitions, and contaminated outputs from untrusted sites" (snippets) — [webmcp#11](https://github.com/webmachinelearning/webmcp/issues/11); [Chrome agent security](https://developer.chrome.com/docs/agents/security); W3C PING tracking — [w3cping#804](https://github.com/w3cping/tracking-issues/issues/804).
- Agent-washing / premature commercialisation: "Multiple commercial ventures launched products and services around WebMCP within days of the Chrome preview, including paid 'Agent Readiness' assessments and enterprise security scanners—all built on a specification that has not defined its own security model"; "selling security tooling for a threat model that doesn't yet exist is not responsible engineering"; the name "creates confusion that is being commercially exploited, as WebMCP is distinct from the Model Context Protocol" (snippet) — [W3C public-aikr list, Feb 2026](https://lists.w3.org/Archives/Public/public-aikr/2026Feb/0015.html).
- Positive voices: Christian Heilmann (2026-02-16), "WebMCP – a much needed way to make agents play with rather than against the web" — [Heilmann](https://christianheilmann.com/2026/02/16/webmcp-a-much-needed-way-to-make-agents-play-with-rather-than-against-the-web/) (blocked; title only); Forbes 2026-02-19 "Google Ships WebMCP, The Browser-Based Backbone For The Agentic Web" — [Forbes](https://www.forbes.com/sites/joetoscano1/2026/02/19/google-ships-webmcp-the-browser-based-backbone-for-the-agentic-web/); the SEO industry has adopted it as a topic (Semrush, SEJ, SEO Inc) — [SEJ](https://www.searchenginejournal.com/webmcp-connects-ai-agents-actions-inside-websites/587303/).

### Inferences
- The criticisms map directly onto why site owners have not authored tools: maintenance cost of a second contract, no consuming agent, unresolved security. That is the demand-side gap a third-party tool builder would fill, but it is also the argument that sites will never author tools at all.
- The loudest excitement is from the tooling/SEO layer, which is the same pattern seen with llms.txt (see Q5): vendors adopt faster than sites.

## Key Question 5: Precedents for agent-facing or capability web standards

### Takeaway
Chromium-only capability APIs (Web Bluetooth 2017, WebUSB) stayed niche for a decade because Safari and Firefox refused; Web Share, which every engine ships, still sits at ~6.6% of pages after eight years; llms.txt, a zero-cost text file with no consuming agent, reached only ~9–10% of top sites in 18 months, mostly via vendor push. The pattern: capability APIs grow only when a platform default (a CMS, a commerce host) turns them on, not through site-by-site authoring.

### Cited Findings
- Web Share: "mobile rising slightly from 6.0% in 2024 to 6.6% in 2025, and desktop from 6.2% to 6.7%" (snippet) — [Web Almanac 2025, Capabilities](https://almanac.httparchive.org/en/2025/capabilities). (Page blocked; figures from snippet.)
- Web Bluetooth: "'the future' since 2017 when Chrome shipped it, and adoption is narrow because of fragmented support (Safari + Firefox refuse)"; 2026 advice: "not bet a product on it without a fallback" (snippet) — [codecrispi.es](https://codecrispi.es/blog/web-bluetooth-2026/); implementation status — [WebBluetoothCG](https://github.com/WebBluetoothCG/web-bluetooth/blob/main/implementation-status.md). WebUSB: "Draft Community status... supported by Chromium-based browsers" — [Wikipedia](https://en.wikipedia.org/wiki/WebUSB).
- llms.txt: "As of June 2026, 8.7% of the world's top 1,000 websites publish an llms.txt"; SE Ranking 300,000-domain study 10.13%; instances grew "from 4,088 to 36,120, an 8.8x increase" to ~38,980 sites by May 2026 (snippets) — [Rankability](https://www.rankability.com/data/llms-txt-adoption/); [DigitalApplied](https://www.digitalapplied.com/blog/llms-txt-in-practice-adoption-evidence-2026); [Casey Burridge scan](https://caseyrb.com/blog/state-of-llms-txt-adoption/).
- Payment Request API: no HTTP Archive adoption figure found; the Almanac notes it only measures APIs that "require neither permission, nor a user gesture" (snippet) — [Web Almanac 2025](https://almanac.httparchive.org/en/2025/capabilities).
- Counter-precedent within WebMCP itself: Shopify's platform-level rollout (Q1) is the mechanism by which a Chromium-only API can reach "millions" of sites in one day — [Shopify changelog](https://shopify.dev/changelog/webmcp-liquid-hydrogen).

### Inferences
- If WebMCP follows Web Bluetooth (Chromium-only, opposed by WebKit), organic authoring by individual sites stays in low single-digit percent for years. If it follows llms.txt, a large scaffold ecosystem forms around ~10% of sites with little evidence of agent consumption. The realistic upside case is "Shopify-style" platform defaults (WooCommerce plugin already listed; Vercel/Netlify/Cloudflare are OpenAI launch partners), which would raise the count without raising the number of sites that author bespoke tools.

### Gaps
- Web Bluetooth/WebUSB/WebHID page-share percentages from HTTP Archive were not retrievable (page blocked, snippets lacked them). No adoption-curve data for Payment Request.

## Key Question 6: Is "most sites have no tools, so users need a tool builder" true today, and in two years?

### Takeaway
True today for the open web outside Shopify: the only crawl (May 2026) found 0 of ~111k top domains, and the self-reported directories total a few hundred mostly small sites; enterprise participants are experimenting, not shipping. In 12–24 months the claim most likely stays true for the long tail and for non-commerce sites, while becoming false for commerce hosted on Shopify and possibly WooCommerce/Vercel-style platforms, and for whichever large brands convert trial to production once Gemini in Chrome and Edge consume tools.

### Cited Findings

### Inferences
- 12-month base case (to Sept 2027): Chrome ships WebMCP in stable around Chrome 157–160; Gemini in Chrome and Edge Copilot call tools; Shopify plus a few platforms account for the overwhelming majority of tool-bearing pages; independently authored tools remain well under 1% of top sites, comparable to Web Bluetooth's trajectory. Safari never implements; Firefox stays neutral.
- 24-month case: two forks. (a) Platform-default spread (WooCommerce, Wix, Squarespace, Webflow, Vercel/Netlify templates) makes "has tools" common for commerce and SaaS templates but still rare for bespoke enterprise apps and the long tail, so a user-side tool builder retains a market on exactly the sites where value is high and no default exists. (b) If WebKit's argument wins and Google's own agent proves it can act from the accessibility tree plus auto browse, WebMCP stalls as a Chromium niche and the tool-builder's value shifts from "fill the WebMCP gap" to "structured actions over any page", independent of the standard.
- Either way, a product should treat `document.modelContext` as one output target (with the `@mcp-b/global` polyfill for non-trial browsers), not as the thesis; the durable need is user-authored structured actions on sites that will not author their own.
- Competitive note: several indie products already do "scan a site, generate tools, inject via extension/embed" (webmcp-forge, WebMCP Today, WebMCP Extension, Refraktor). None appears to have traction data, but the space is not empty.

### Gaps
- No independent measurement of Shopify storefronts actually being invoked by any agent, nor of Gemini-in-Chrome or Edge consuming tools in a shipping build.
- No post-trial (post-Sept 2026) crawl of top sites for runtime tools; the "0%" figure is four months old and predates the two biggest adoption events.
- Could not confirm whether the Chrome origin trial will be extended versus shipped; Chrome 157 is a Chrome Status placeholder, not an announced intent.

## Key Question 1 — Demand signals: do people want this, and who is the user?

### Takeaway
Demand for browser agents is large and still growing (Browser Use ~116k stars gaining ~2k/week; Claude in Chrome ~15M Chrome Web Store users; OpenClaw 390k stars), and there is a visible sub-demand for "record once / make the site a tool" (workflow-use, webpage-mcp, Cloudflare's WebMCP proxy). The user who cares about reusable, cost-capped, reviewable site tools is a developer or technical power user, not a consumer — consumers are being served by Claude in Chrome, Gemini in Chrome, Comet and ChatGPT's Chrome extension.

### Inferences
- The consumer "agentic browser" slot is being consolidated by platform owners (Claude in Chrome, Gemini in Chrome, ChatGPT Chrome extension, Comet); a standalone Electron browser competing on *general* browsing is a bad bet. Toolsmith's defensible angle is the developer-facing one: reusable, reviewable, versioned site tools that a Claude Code / Codex session can call.
- The star velocity of `jev-ultrafast` (18k stars in a week, pitched as "fastest and cheapest") and `browser-harness` suggests the market's current pain is cost and speed, not capability — exactly what tool reuse attacks.
- The user is a developer or technical ops person who already runs Claude Code / Codex and wants sites-without-APIs to become callable tools. Consumers won't review, disable, or roll back tools.

## Key Question 2 — Economics: cost per browser-agent task and what a reusable tool saves

### Takeaway
At Sept-2026 list prices, an exploration-style 10-step task costs roughly $0.04–$0.40 depending on model and caching; a saved tool called on the second run costs roughly a cent on Sonnet 5 or nothing if replayed deterministically — a 90–100% reduction. Anthropic's own docs put the browser-use toolset overhead at ~6,600 input tokens per request, which prompt caching cuts to ~10% after the first call.

### Cited Findings
- Anthropic first-party list prices (per MTok, page fetched 2026-09-23): Claude Opus 5 $5 in / $25 out, 5-min cache write $6.25, cache read $0.50; Claude Opus 5.5 $4 / $20, cache read $0.20; Claude Sonnet 5 $2 / $10, cache read $0.20; Claude Haiku 4.5 $1 / $5, cache read $0.10; Claude Fable 5.1 $10 / $50, cache read $0.25 — [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Sonnet 5's $2/$10 "introductory" price is now permanent: "The previously scheduled increase to $3/$15 ... on September 1, 2026 will not occur" — [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Prompt caching multipliers: 5-minute write 1.25× base input, 1-hour write 2×, read 0.1× (0.05× on Opus 5.5, 0.025× on Fable 5.1); "caching pays off after one cache read for the 5-minute duration"; Batch API is 50% off and stacks with caching — [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Claude 4.7+ models "use a newer tokenizer ... approximately 30% more tokens for the same text" — [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Anthropic's browser use toolset (`browser_toolset_20260801`) "adds about 6,600 input tokens to a request" (6,610 on Opus 5, 6,670 on Sonnet 5); computer use toolset adds ~4,500; screenshots are billed as image input; text results such as "accessibility trees, page text, and console or network entries" are billed as input tokens — [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Anthropic's web-fetch sizing guide: average 10 kB web page ≈ 2,500 tokens; 100 kB documentation page ≈ 25,000 tokens — [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Anthropic's worked example: a one-hour Opus 5 session with 50k input / 15k output = $0.625 in tokens ($0.25 + $0.375); with 40k of the input as cache reads it drops to $0.445 — [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Practitioner token math (dev.to, blocked; snippet): accessibility-tree snapshots ≈ 800 tokens per page versus "thousands" for screenshots; "ten turns on screenshots alone would be ~3.5M tokens of image content, while ... on accessibility trees is ~5K tokens" — [dev.to siropkin](https://dev.to/siropkin/accessibility-tree-vs-screenshots-the-token-math-behind-my-browser-agent-3fk9) (snippet only, unverified)
- Another practitioner post claims a screenshot-driven agent "burns 114,000 tokens reading one page" and a 10-step task drops to ~3,000 tokens on accessibility trees ("97% less") — [getnadir.com](https://getnadir.com/blog/browser-agent-token-cost-screenshots-accessibility-tree/) (snippet only, unverified)
- A search summary estimates "a multistep browser task can consume 20,000 to 60,000 tokens ... costing roughly $0.10 to $0.30 per task at $5 per million input tokens on a frontier model" — [search aggregate of dev.to/leonting1010](https://dev.to/leonting1010/your-ai-browser-agent-costs-3600month-heres-how-to-make-it-0-4228) (snippet only, unverified)
- OpenAI GPT-5.5 API list price reported by third-party aggregators as $5.00 / MTok input, $30.00 / MTok output, cached input $0.50 / MTok (10%), 1M-class context, batch 50% off — [morphllm](https://www.morphllm.com/openai-api-pricing), [markaicode](https://markaicode.com/pricing/openai-api-gpt-55-pricing-cost-per-million-tokens/) (openai.com blocked; **unverified against official page**; aggregators also mention GPT-5.6 and GPT-5.4 exist but no numbers were retrievable)
- workflow-use claims deterministic replays run "with no LLM calls" — [browser-use/workflow-use](https://github.com/browser-use/workflow-use)

### Inferences
Worked estimates (my arithmetic on the official Anthropic prices above; assumptions stated):
- **Exploration run** (Builder mode): 10 model turns, accessibility-tree page state, ~6k input tokens/turn including the ~6.6k toolset overhead amortised via caching, total ≈ 60k input / 3k output. Uncached: Opus 5 ≈ $0.30 + $0.075 = **$0.38**; Sonnet 5 ≈ $0.12 + $0.03 = **$0.15**; Haiku 4.5 ≈ $0.06 + $0.015 = **$0.075**; GPT-5.5 (aggregator price) ≈ $0.30 + $0.09 = **$0.39**. With ~70% of input served from cache: Opus 5 ≈ **$0.19**, Sonnet 5 ≈ **$0.07**, Haiku 4.5 ≈ **$0.035**.
- **Screenshot-driven run**: image tokens dominate; using the practitioner claim of ~100 kB screenshots and Anthropic's own note that screenshots bill as image input, a 10-step vision run is plausibly 10–50× the token count of the tree run (order of $1–$5 on Opus 5). Treat as an order-of-magnitude estimate, not a measurement.
- **Second run with a saved tool**: one tool call — tool schema (~300 tokens) + arguments + a trimmed result (~1–2k tokens), ~3k input / 200 output ≈ Sonnet 5 **$0.008**, Opus 5 **$0.02**; or **$0** if Toolsmith replays the saved script deterministically without a model in the loop (workflow-use's pattern). Savings ≈ 95–100% per repeat, plus wall-clock: one call instead of ten round-trips.
- Prompt caching is the largest lever for exploration cost: the toolset definition and system prompt (~7k+ tokens) are byte-identical across turns and should sit under a cache breakpoint; the pricing page's "pays off after one read" rule means every multi-step task benefits.

## Key Question 3 — Subscription vs API-key constraint, and the safest design

### Takeaway
Anthropic's position is now explicit and enforced: subscription OAuth is only for the unmodified Claude Code binary and native apps; third-party apps must not offer Claude.ai login, route through Pro/Max credentials, or store Claude session tokens — but an end user *may* sign into unmodified Claude Code themselves, and Agent SDK / `claude -p` / third-party usage currently still draws on subscription limits (the separate-credit plan was paused 2026-06-15). OpenAI has no explicit written position on "Sign in with ChatGPT" from third-party apps; staff have declined to clarify since Dec 2025. The safest design is to spawn the user's own unmodified `claude` / `codex` CLI as a subprocess (or Agent SDK) and never touch their tokens, with API keys as the first-class alternative.

### Cited Findings
- Anthropic legal page (fetched 2026-09-23): "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." — [code.claude.com legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Same page: "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." — [code.claude.com](https://code.claude.com/docs/en/legal-and-compliance)
- Same page, the carve-out: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code"; conditions for embedding: "The Claude Code binary must not be modified ... customers may not remove, disable, or restrict any authentication method built into it" and "Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential"; also "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice" and "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK" — [code.claude.com](https://code.claude.com/docs/en/legal-and-compliance)

### Inferences
- Three auth designs, ranked by safety:
  1. **Subprocess / Agent-SDK delegation (safest).** Toolsmith shells out to the user's installed, unmodified `claude` (interactive or `-p`, or via `@anthropic-ai/claude-agent-sdk`) and `codex` binaries, exposing its browser as an MCP server to them. The user logs in through Anthropic's/OpenAI's own flow; Toolsmith never sees a token. This matches the legal page's explicit carve-out, and the June-2026 help article says such usage currently draws from plan limits. Risk: the paused "separate credit" plan could return and cap it; enforcement of "ordinary, individual usage" is discretionary.
  2. **BYO API key (always allowed).** Anthropic Console key or OpenAI key; pay-as-you-go. Should be first-class, not a fallback.
  3. **Reading `~/.claude/.credentials.json` or implementing Claude.ai OAuth in-app (do not do).** This is the opencode-claude-auth pattern and is exactly what the legal page prohibits; pi #9838 shows enforcement by system-prompt fingerprinting in Sept 2026.
- For Codex, the same subprocess design is the only defensible one given OpenAI's silence: let the unmodified CLI handle "Sign in with ChatGPT"; do not embed the OAuth flow.
- Marketing copy should say "runs on your Claude Code / Codex subscription via the official CLIs" and never use Claude/Anthropic in the product name or logo.

### Gaps
- No official OpenAI document addressing third-party use of ChatGPT sign-in was found; the only primary signal is a non-answer from OpenAI staff. openai.com and developers.openai.com were blocked, so the current Codex auth docs were not read directly.
- Whether Anthropic's Sept-2026 "extra usage" enforcement against pi also affects Agent SDK / `claude -p` subprocess usage is not documented anywhere found; the June-16 help article is the last official word.
- Goose's and Cline's current subscription-auth handling was not located in this pass.

## Key Question 4 — Portfolio credibility: what made individual-developer agent projects noticed

### Takeaway
The projects that broke out in 2025–26 (Browser Use, pi, OpenClaw, Nanobrowser) shared a "magical moment" demo, a benchmark number (Index's 92% WebVoyager), a tiny, legible core (pi's <1k-token system prompt, four primitives), and public evals; hiring-side guidance for 2026 values a tool you actually use, explained tradeoffs, and proof of shipping over volume.

### Inferences
- For a senior frontend candidate, the credibility surface is: (a) a 60–90 s demo of Builder mode creating, verifying and re-running a tool; (b) one honest benchmark table — cost and wall-clock for exploration vs saved-tool runs on 5–10 real sites, with the arithmetic from Key Question 2; (c) a README that states the auth decision (subprocess delegation, never token intermediation) and the tradeoff it cost; (d) an eval/test suite that replays saved tools against recorded fixtures; (e) evidence of daily personal use.
- The bar for "noticed" is inflated by 100k-star outliers; realistic and still valuable is a well-received Show HN plus a handful of external users, which also satisfies the hiring-guide "strangers signed up" category.

## Key Question 5 — Viability risk: native browser agents and WebMCP making a standalone app redundant

### Takeaway
The redundancy risk is real and near-term for *general* browsing: WebMCP is in Chrome origin trial (146 Canary, Feb 2026) with a pencilled stable target of Chrome 157 (2026-11-03), Gemini in Chrome will call it, and Anthropic/OpenAI/Google/Perplexity all ship consumer browser agents. What none of them ship is a local, user-authored, versioned tool store with review/disable/rollback — and WebMCP only works where site owners opt in, leaving the long tail to something like Builder mode.

### Cited Findings
- WebMCP shipped in Chrome 146 Canary on 2026-02-10; an origin trial covers Chrome up to 156; Chrome Status "pencils in Chrome 157 (out 3 November 2026) as the anticipated milestone for stable release, though it's a target rather than a committed ship date"; Firefox and Safari are "engaged in the spec process but haven't committed to timelines"; Google said Gemini in Chrome "will soon support WebMCP APIs" — [dev.to compatibility status](https://dev.to/ai-agent-economy/webmcp-in-2026-which-browsers-support-navigatormodelcontext-complete-compatibility-status-1oe4), [Chrome Status 5117755740913664](https://chromestatus.com/feature/5117755740913664), [Spronta State of WebMCP July 2026](https://www.spronta.com/blog/state-of-webmcp-july-2026/) (all three blocked; snippets only), [Forbes 2026-02-19](https://www.forbes.com/sites/joetoscano1/2026/02/19/google-ships-webmcp-the-browser-based-backbone-for-the-agentic-web/), [blink-dev Intent to Experiment](https://groups.google.com/a/chromium.org/g/blink-dev/c/gmYffo5WOE8/m/OJxuQRP3AAAJ)

### Inferences
- Timeline: WebMCP stable in Chrome plausibly Q4 2026 (target 2026-11-03, not committed), Edge shortly after; Gemini-in-Chrome and Claude-in-Chrome will consume site-published tools first. Even OpenAI abandoned the standalone-browser form factor in favour of extensions and the desktop app — a warning against positioning Toolsmith as "a browser".
- What remains open through at least 2027: (1) the long tail of sites that will never publish WebMCP tools (Builder mode synthesises them), (2) local ownership — reviewable, versioned, disable/rollback tool definitions that a Claude Code / Codex session can call as MCP, and (3) cost control by replaying saved tools without a model in the loop. Vendors' consumer agents optimise for the opposite (fresh exploration each time, on their own metered plans).
- Positioning that survives: "an MCP server + tool workshop for sites without APIs, running in your own Chromium, on your own CLI subscriptions" rather than "an agentic browser". Consuming native WebMCP tools when present keeps it forward-compatible instead of competing with the standard.

# Toolsmith "Built tool" runtime, package format and store

Scope: the tool module API, compile → inject → register → verify pipeline, sandboxing model and its limits, on-disk store, export/import package format, and the verification-evidence model for Built tools (agent-generated TypeScript modules that register WebMCP tools into an embedded site's page from an isolated world over CDP). Dated 2026-09-23. Local clones read: WebMCP spec (`webmcp`, HEAD f5645e9, 2026-09-17), `devtools-protocol` (HEAD 95987cc, 2026-09-22, "Roll protocol to r1702366"), DeepDeck (HEAD 5c3ce0b, 2026-09-17), OpenTabs (HEAD de9200b, 2026-07-27), Electron `DEPS` (Chromium `152.0.7977.130`, Node `v24.21.0`), Blink `runtime_enabled_features.json5` (`ref.json5`). Items marked **[unverified]** could not be checked against a primary source through the proxy.

## KQ1. WebMCP `registerTool` shape, annotations, CDP surface, isolated-world behaviour, polyfill fallback

### Takeaway
As of the 2026-09-17 spec, `registerTool(ModelContextTool, {signal, exposedTo})` takes `{name, title?, description, inputSchema?, execute, annotations?}`; names are 1–128 chars of `[A-Za-z0-9_.-]`, so `toolsmith.<site>.<name>` is legal. Chromium keeps one tool map per `Document` (a `Supplement<Document>`), so a tool registered from a CDP isolated world lands in the same registry the page and CDP see — DeepDeck ships on exactly this, and its own tests assert that an isolated-world registration collides with a page-registered name. CDP's experimental `WebMCP` domain surfaces annotations as `readOnly/untrustedContent/consequential/debugging/autosubmit` and invokes tools with `WebMCP.invokeTool({frameId, toolName, input})`.

### Cited Findings

**Spec shape (webmachinelearning/webmcp `index.bs`, HEAD f5645e9, 2026-09-17)**
- IDL: `dictionary ModelContextTool { required DOMString name; USVString title; required DOMString description; object inputSchema; required ToolExecuteCallback execute; ToolAnnotations annotations; }`; `callback ToolExecuteCallback = Promise<any> (object inputObject, ToolExecuteCallbackOptions options)`; `ToolExecuteCallbackOptions { required AbortSignal signal }` — [index.bs L1083–1104](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- `ToolAnnotations { readOnlyHint=false; untrustedContentHint=false; consequentialHint=false; debugging=false }`. Definitions: readOnlyHint "does not modify any state and only reads data"; untrustedContentHint "output contains data that is untrusted, from the perspective of the author registering the tool"; consequentialHint "consequential actions that are significant, real-world, or non-reversible, ex: booking a flight, transferring money"; debugging "intended for debugging and developer tooling" — [index.bs L1094–1160](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- `ModelContextRegisterToolOptions { sequence<USVString> exposedTo; AbortSignal signal; }` — "An AbortSignal that unregisters the tool when aborted"; `exposedTo` origins must be potentially-trustworthy or registration rejects with `SecurityError` — [index.bs L1180–1192, L718–727](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- Name rule: "length must be between 1 and 128, inclusive, and only consist of ASCII alphanumeric code points, U+005F (_), U+002D (-), and U+002E (.)"; violations, duplicate names, and empty description reject with `InvalidStateError`; `inputSchema` is JSON-stringified at registration and a throwing/circular value rejects — [index.bs L158–160, L683–708](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- `ModelContext` interface: `registerTool`, `getTools(options)`, `executeTool(RegisteredTool, inputObject, {signal})`, events `toolchange`, `toolactivated`, `toolcancel` (the last two added in PR #245, the HEAD commit) — [index.bs L615–624](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- Cancellation: when the agent aborts, the per-execution AbortController is signalled, a `toolcancel` event fires at the document's ModelContext, and the `executeTool` promise "will still be rejected with the abort reason, and will never observe the tool's natural resolution/rejection" — [index.bs L260–296](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- The spec's own "swap a tool's schema" idiom is register-with-signal → `ac.abort()` → register again — [index.bs L442–449](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- `RegisteredTool` (what `getTools()` returns) carries `name, title, description, inputSchema (deep copy), window, origin, annotations` — [index.bs L1239–1246](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- Interface is `[Exposed=Window, SecureContext]` — HTTPS (or localhost) only — [index.bs L614](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)

**CDP `WebMCP` domain (ChromeDevTools/devtools-protocol `browser_protocol.json`, r1702366)**
- Domain is `experimental`, depends on `Runtime, Page, DOM`. `Annotation { readOnly?, untrustedContent?, consequential?, debugging?, autosubmit? }` — note CDP drops the `Hint` suffix that the JS API uses — [browser_protocol.json L30781+](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)
- `Tool { name, description, inputSchema?, annotations?, frameId, backendNodeId? (declarative), stackTrace? ("The stack trace at the time of the registration") }` — same
- Commands: `enable` ("Enabling the domain will trigger a toolsAdded event for all currently registered tools"), `disable`, `invokeTool({frameId, toolName, input:object}) → {invocationId}` ("Response is sent before tool events"), `cancelInvocation({invocationId})` — same
- Events: `toolsAdded{tools[]}`, `toolsRemoved{tools[{name, frameId}]}`, `toolInvoked{toolName, frameId, invocationId, input:string}`, `toolResponded{invocationId, status: Completed|Canceled|Error, output?: any, errorText?, exception?: Runtime.RemoteObject}`; the `output` doc says "The output is untrusted and poses a prompt injection risk. Clients should treat this as potentially malicious user input." — same
- The `stackTrace` on registration is how a host can tell *which world/script* registered a tool without relying on the tool's name (inference from the field's presence; DeepDeck instead uses a binding receipt, below).

**Does a tool registered from an isolated world reach the page and CDP?**
- Chromium's `ModelContext` is stored as `Supplement<Document>` (`model_context_supplement.cc` L17–38) and `registerTool` rejects `"Duplicate tool name"` against a single `tool_map_` (`model_context.cc` L370–373). There is one map per Document, not per V8 world; the `execute` callback is held as a `V8ToolExecuteCallback` and invoked via `tool_function->Invoke(...)` (L782), which V8 bindings run in the callback's own creation context — [chromium/src third_party/blink/renderer/core/script_tools/model_context.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/script_tools/model_context.cc), [model_context_supplement.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/script_tools/model_context_supplement.cc)
- Two extra gates in `registerTool` that an isolated-world script cannot get around: `IsModelContextAllowed()` (rejects with `SecurityError`, `kDocumentDomainEnabledError`, i.e. when the page set `document.domain`) and Permissions-Policy feature `kTools` (rejects `NotAllowedError` when `tools` is disallowed for the frame) — [model_context.cc L347–367](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/script_tools/model_context.cc)
- DeepDeck relies on this: it injects into an isolated world named `deepdeck-webmcp` via `Page.addScriptToEvaluateOnNewDocument({source, worldName: WEBMCP_WORLD})`, calls `document.modelContext.registerTool(...)` from there, listens to `WebMCP.toolsAdded` to learn the tool arrived, and later invokes with `WebMCP.invokeTool({frameId, toolName, input})` — [browser-window.ts L324, L276–291, L999](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-window.ts); [browser-webmcp-script.ts](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-webmcp-script.ts)
- DeepDeck's bootstrap comment: "registerTool itself rejects collisions, preserving existing native tools", and its unit test "rolls back partial registration after a source error and preserves site collisions" expects `Duplicate tool` when the isolated-world script registers a name the page already holds — [browser-webmcp-script.ts L27](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-webmcp-script.ts); [browser-webmcp-script.test.ts L59–63](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-webmcp-script.test.ts)
- DeepDeck's builder skill tells the agent the script "runs in an isolated JavaScript world on the exact matching origin. It can inspect the page DOM, but page-owned JavaScript globals may not be accessible" and to call `document.modelContext.getTools()` / `executeTool(tool, input)` to compose with site-declared tools — [builder-skill.ts](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/builder-skill.ts)
- Extension-world pattern in the wild: MCP-B's extension has the MAIN world install `document.modelContext` (native or polyfill) and the isolated content script host the MCP client — [WebMCP-org/npm-packages](https://github.com/WebMCP-org/npm-packages); [dev.to write-up](https://dev.to/tanahiro2010/i-built-a-bridge-for-googles-new-webmcp-draft-spec-heres-what-broke-1691)

**Polyfill fallback when the site has no native `document.modelContext`**
- `@mcp-b/global@5.1.0` (published 2026-08-31, engines node>=20): "implements the WebMCP API (`document.modelContext`)"; IIFE build `dist/index.iife.js` is 285 KB minified and "Auto-detects and uses native browser implementation when available"; ESM ~16 KB without bundled deps — [npm](https://registry.npmjs.org/@mcp-b/global); [README](https://github.com/WebMCP-org/npm-packages/blob/main/packages/global/README.md)
- `@mcp-b/webmcp-polyfill@5.1.0` (2026-08-31): "Strict WebMCP core runtime polyfill for document.modelContext (with deprecated navigator.modelContext alias)"; exports `.`, `./schema`, `./iife` — the smaller, spec-only choice — [npm](https://registry.npmjs.org/@mcp-b/webmcp-polyfill)
- README explicitly lists `@mcp-b/webmcp-types` for types only, `@mcp-b/webmcp-polyfill` for "strict WebMCP runtime polyfill behavior", `@mcp-b/global` for MCP-B extras (bridge transport, prompts/resources) — [README](https://github.com/WebMCP-org/npm-packages/blob/main/packages/global/README.md)

### Inferences
- Because the tool map is per-Document, the page's own `getTools()` *will* list Toolsmith's Built tools (they must, since agents "cannot tell them apart" per the glossary). This is desirable for composition but means a hostile page script can call `executeTool` on a Built tool. Mitigation is the `writes` Approval gate living in the app's MCP layer, not in the page (Toolsmith `CONTEXT.md`), and the namespace prefix makes shadowing impossible in both directions since `registerTool` rejects duplicates.
- The polyfill should be loaded **only in the isolated world**, and only when `document.modelContext` is absent there, and then it is invisible to CDP `WebMCP.*` (the CDP domain reads Blink's native registry, not a JS object). So on Electron 43+/Chromium 152 with `enableBlinkFeatures: "WebMCP"`, prefer native and treat the polyfill path as "Toolsmith-only tools that Declared-tool discovery cannot see" — invocation must then go through `Runtime.callFunctionOn` on a Toolsmith-owned registry object, not `WebMCP.invokeTool`. Design consequence: keep an app-side invoker abstraction with two backends (native CDP vs polyfill/JS bridge).
- A site can shut WebMCP off for everyone (Permissions-Policy `tools`), and `document.domain` use disables it. Toolsmith's UI needs a distinct "site disallows WebMCP" state (DeepDeck reports `WebMCP is unavailable or disabled by this site`).

### Gaps
- Could not fetch developer.chrome.com (`secure-tools`, `best-practices`) through the proxy; how Chrome's own agent renders annotations in UI is not verified here.
- Whether `WebMCP.invokeTool` from CDP runs `execute` with the isolated world's `location`/globals is inferred from the V8 callback-context rule and DeepDeck's working code, not from an explicit Chromium test I read.
- The exact Chromium milestone where `Annotation.autosubmit` and the `debugging` hint landed was not checked.

## KQ2. Tool module API: a minimal typed SDK, compared with OpenTabs and DeepDeck

### Takeaway
OpenTabs proves a Zod-4 `defineTool({name, description, input, output, handle})` SDK compiled with esbuild to an IIFE and converted with `z.toJSONSchema()` works at scale (100+ plugins); DeepDeck proves the leaner "single TS file, runtime-provided `globalThis.__sdk.registerTool` + `signal` + `onDispose`" contract works inside a CDP isolated world. Toolsmith should combine them: Zod-typed `defineTool` in source, JSON Schema derived at build time and frozen into the manifest/contract, and a runtime-injected `ctx` (`http`, `dom`, `signal`, `log`) rather than free globals.

### Cited Findings

**OpenTabs `@opentabs-dev/plugin-sdk` 0.0.115 (HEAD de9200b, 2026-07-27)**
- `ToolDefinition<TInput extends z.ZodObject, TOutput extends z.ZodType> { name; displayName?; description; summary?; icon?; group?; input: TInput; output: TOutput; handle(params: z.infer<TInput>, context?: ToolHandlerContext): Promise<z.infer<TOutput>> }`; "Tool name — auto-prefixed with plugin name (e.g., 'send_message' → 'slack__send_message')"; `defineTool` is an identity function for inference — [platform/plugin-sdk/src/index.ts L43–71](https://github.com/opentabs-dev/opentabs/blob/main/platform/plugin-sdk/src/index.ts)
- `OpenTabsPlugin` abstract class: `name`, `description`, `urlPatterns` (Chrome match patterns), `excludePatterns?`, `homepage?`, `configSchema?`, `tools`, `isReady()`, `displayName`, lifecycle `teardown?()`, `onActivate?()`, `onDeactivate?()` ("onDeactivate fires before teardown") — same file L77–140
- Zod dependency `"zod": "^4.4.3"`; manifest/registration schemas produced with `z.toJSONSchema(tool.input)` and `z.toJSONSchema(tool.output)` at build (`plugin-tools/src/commands/build.ts` L416–427) and at MCP setup (`mcp-server/src/mcp-setup.ts` L94) — [opentabs repo](https://github.com/opentabs-dev/opentabs)
- Handlers run in the page's MAIN world: extension injects with `chrome.scripting.executeScript({ world: 'MAIN' ... })` (`iife-injection.ts` L31–59), and the SDK ships a `fetch.ts` helper (`FetchFromPageOptions extends RequestInit { timeout?: number }`, default 30 s; HTTP status → `ToolError` categories auth/notFound/rateLimited/validation/timeout/internal with `retryable` and `retryAfterMs`) — [plugin-sdk/src/fetch.ts](https://github.com/opentabs-dev/opentabs/blob/main/platform/plugin-sdk/src/fetch.ts)
- Bundling: `esbuild({ ..., format: 'iife' })` with a plugin that marks `node:*` imports as side-effect-free externals so unused Node builtins tree-shake out of the adapter IIFE — [plugin-tools/src/commands/build.ts L710–1009](https://github.com/opentabs-dev/opentabs/blob/main/platform/plugin-tools/src/commands/build.ts)
- Example plugin (Hacker News) exports `new HackerNewsPlugin()` with 10 `ToolDefinition`s and `isReady()` polling `document.readyState` — [plugins/hackernews/src/index.ts](https://github.com/opentabs-dev/opentabs/blob/main/plugins/hackernews/src/index.ts)

**DeepDeck builder contract**
- Runtime-provided global: `interface WebMCPBuilderSDK { readonly signal: AbortSignal; registerTool(tool: { name; description; inputSchema: Record<string,unknown>; execute(input): unknown|Promise<unknown> }): Promise<string>; onDispose(cb): void }`; "The SDK adds the `deepdeck_` prefix if it is absent"; "the runner waits for all registration Promises started during initialization" (10 s deadline in the bootstrap) — [builder-skill.ts](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/builder-skill.ts); [browser-webmcp-script.ts L44–49](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-webmcp-script.ts)
- Constraints stated to the agent: "single TypeScript browser script … The fixed compiler creates an IIFE; no package installation, runtime imports, require(), arbitrary build commands, or Node APIs are available. Type-only declarations are permitted." Tools "cannot call Harness tools or start another model turn"; "Tie fetches and listeners to sdk.signal … release timers, observers … with sdk.onDispose"; "Do not return credentials, cookies, authorization headers, or unrelated network bodies" — same
- Bootstrap wraps every `execute` to throw `'This WebMCP version is no longer active.'` once the version's controller is aborted, and registers each tool with `{ signal: controller.signal }` so `dispose()` unregisters everything without a reload — [browser-webmcp-script.ts L28–33, L37–42](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-webmcp-script.ts)
- Name validation in DeepDeck is `/^[a-zA-Z0-9_-]{1,128}$/` (no dot) — stricter than the spec, which allows `.` — [browser-webmcp-script.ts L26](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-webmcp-script.ts)

**Schema libraries (npm registry, 2026-09-23)**
- `zod@4.6.5` (2026-09-13). `z.toJSONSchema(schema, { target: "draft-2020-12" | "draft-07" | "draft-04", metadata, unrepresentable: "throw" | "any", cycles: "ref" | "throw", reused: "inline" | "ref", io: ... })`; default target draft-2020-12; unrepresentable types throw by default — [zod docs json-schema.mdx](https://github.com/colinhacks/zod/blob/main/packages/docs/content/json-schema.mdx); [npm](https://registry.npmjs.org/zod)
- `@sinclair/typebox@0.34.52` (2026-07-11): "Json Schema Type Builder with Static Type Resolution" — schemas *are* JSON Schema objects, no conversion step — [npm](https://registry.npmjs.org/@sinclair/typebox)
- The WebMCP spec stringifies whatever object is passed as `inputSchema` and does not validate it as JSON Schema at registration (only that it JSON-serialises) — [index.bs L693–708](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)

### Inferences (proposed Toolsmith SDK)
- Source-side API, in a tiny `@toolsmith/sdk` that only ships types plus `defineTool`/`z` re-export:
  ```ts
  import { defineTool, z } from "@toolsmith/sdk";
  export default defineTool({
    name: "list_open_issues",           // app prefixes toolsmith.<site>.
    description: "...",
    input: z.object({ repo: z.string(), state: z.enum(["open","closed"]).default("open") }),
    output: z.object({ issues: z.array(z.object({ number: z.number(), title: z.string() })) }),
    trust: "read",                       // agent's *claim*; app assigns the real Trust class
    async execute(input, ctx) { /* ctx.http, ctx.dom, ctx.signal, ctx.log */ }
  });
  ```
  `ctx.http(url, init?)` is the Toolsmith-owned `http()` helper (KQ4); `ctx.dom` = `{ query, queryAll, text, click, setValue, waitFor(selector|predicate, {timeout}) }` wrappers that use verified input paths (DeepDeck's guidance that "setting a value attribute … is not proof the application accepted the edit"); `ctx.signal` is the per-call `AbortSignal` from `ToolExecuteCallbackOptions` chained with the version's dispose signal.
- Zod 4 is the right pick over TypeBox: OpenTabs already runs it in-page, `z.toJSONSchema` is first-party, and the input schema can be evaluated once **at build time in the main process** (so the page bundle doesn't have to carry Zod at all if the SDK's build step strips it — [unverified: whether a schema-only stub is practical]). If bundle size matters, TypeBox's "schema is the JSON" removes the conversion step but loses the runtime `.parse()` ergonomics the Builder agent is used to. Freeze the generated `inputSchema` into the version's `contract.json`; at runtime the bootstrap passes that frozen object to `registerTool`, so a drift between source and contract is impossible by construction.
- Use `annotations` exactly per Trust class: `read` → `readOnlyHint: true`; `writes` → `consequentialHint: true` (defaults false); always `untrustedContentHint: true` because every Built tool's output is site content. Set them from the *app's* Trust class, not from the agent's `trust` claim (glossary: "Assigned by the app after review, never by the agent").

### Gaps
- No public "canonical" WebMCP SDK for generated tools exists yet beyond `@mcp-b/*`; both comparators are proprietary contracts. The proposed shape is a synthesis, not a found artifact.
- Whether Zod 4 can be tree-shaken to a size acceptable for injection into every same-origin document was not measured.

## KQ3. Compile / inject / register / verify pipeline

### Takeaway
DeepDeck's pipeline is the closest working precedent: esbuild (`bundle`, `format:'iife'`, `platform:'browser'`, `target:['es2022']`, an `onResolve` plugin that errors on every import) in the Electron main process, SHA-256 digests of source and bundle folded into a revision id, `Page.addScriptToEvaluateOnNewDocument({worldName})` plus an immediate `Runtime.evaluate` in a freshly `createIsolatedWorld`'d context for already-loaded pages, self-gating on `location.origin` and `self === top`, a `Runtime.addBinding` receipt channel for registration reports, and an `AbortController` per version that unregisters without reload. Toolsmith can adopt it nearly verbatim and add `target: 'chrome152'`, `runImmediately: true`, and a frozen-helper banner.

### Cited Findings
- esbuild `0.28.2` (2026-08-08, node>=18) — [npm](https://registry.npmjs.org/esbuild). DeepDeck pins `^0.25.0` and records `compiler: esbuild@${version}` in every revision manifest — [webmcp-store.ts L6, L216](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-store.ts)
- DeepDeck compile options: `stdin {contents, sourcefile:'webmcp.ts', loader:'ts'}, bundle:true, write:false, platform:'browser', format:'iife', target:['es2022'], charset:'utf8', legalComments:'none', sourcemap:false, logOverride:{'unsupported-dynamic-import':'error','unsupported-require-call':'error'}`, plus plugin `webmcp-no-runtime-imports` whose `onResolve({filter:/.*/})` returns an error for any import ("esbuild passes this expression to Go's regexp engine, which has no /u flag"). Caps: source 512 KiB, compiled 1 MiB — [webmcp-store.ts L188–212](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-store.ts)
- esbuild `target` accepts environment names `chrome, deno, edge, firefox, hermes, ie, ios, node, opera, rhino, safari` plus versions (`es2020`…), e.g. `--target=es2020,chrome58`; "only concerned with syntax features, not APIs"; `banner`/`footer` insert "an arbitrary string at the beginning [end] of generated JavaScript and CSS files" per file type (`banner: { js: '...' }`) — [esbuild API docs source](https://github.com/esbuild/esbuild.github.io/blob/main/src/content/api.yml)
- Version id: DeepDeck `revisionId = sha256(JSON.stringify([origin, sourceDigest, compiledDigest, compiler, provenance?, upstream?]))` where digests are `sha256` hex of the text; the id is asserted to match `/^[a-f0-9]{64}$/` and is recomputed from `revision.json` on every read (`revisionId(value) !== revision` → "metadata is invalid") — [webmcp-store.ts L70–78, L360–372](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-store.ts)
- Injection: `Page.addScriptToEvaluateOnNewDocument({ source: webmcpBootstrap(script), worldName: WEBMCP_WORLD })`, storing the returned `identifier` so a re-install first calls `Page.removeScriptToEvaluateOnNewDocument` — [browser-window.ts L320–326](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-window.ts)
- CDP doc: `addScriptToEvaluateOnNewDocument` "Evaluates given script in every frame upon creation (before loading frame's scripts)"; `worldName` (experimental) "creates an isolated world with the given name and evaluates given script in it. This world name will be used as the ExecutionContextDescription::name"; `runImmediately` (experimental) "If true, runs the script immediately on existing execution contexts or worlds. Default: false." — [browser_protocol.json Page domain](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)
- DeepDeck does not use `runImmediately`; for an already-loaded page it calls `Page.createIsolatedWorld({frameId: mainFrameId, worldName})` then `Runtime.evaluate({expression, contextId, awaitPromise:true, returnByValue:true, timeout:15000})` — [browser-window.ts L308–318, L349–352](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-window.ts)
- `Page.createIsolatedWorld` params: `frameId`, `worldName?`, `grantUniveralAccess?` ("powerful option, use with caution"), and a **`contentSecurityPolicy?`** string: "An optional content security policy to set for the isolated world. If omitted, any existing CSP for the world will be cleared … takes effect on subsequent navigations" — [browser_protocol.json](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json). DeepDeck's CDP policy forces `grantUniveralAccess = false` on any proxied `createIsolatedWorld` — [browser-devtools-policy.ts L54–58](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-devtools-policy.ts)

### Inferences (Toolsmith pipeline)
1. **Compile** (main process): esbuild 0.28.x `{ stdin: {contents, loader:'ts'}, bundle:true, write:false, platform:'browser', format:'iife', target:['chrome152'], charset:'utf8', legalComments:'none', sourcemap:'inline' (kept only in the version folder, stripped from the injected copy), minify:false, banner:{js: FROZEN_PRELUDE}, footer:{js: ''} }`. Resolve plugin: allow only `@toolsmith/sdk` (mapped to a virtual module that exports `defineTool`, `z`), error on everything else. Record `compiler`, `target`, `sdkVersion` in the manifest.
2. **Hash**: `version = sha256(bundle.js)` as the folder name; also store `sha256(source.ts)` and `sha256(contract.json)`; a combined `revisionId` like DeepDeck's makes provenance part of identity.
3. **Inject**: one `Page.addScriptToEvaluateOnNewDocument({ source: bootstrap(version), worldName: 'toolsmith', runImmediately: true })` per site; keep the identifier for removal. `runImmediately` replaces DeepDeck's manual `createIsolatedWorld`+`evaluate` for the current document [unverified on Electron 43's Chromium — DeepDeck avoided it, reason unknown]. Bootstrap gates on `location.origin === SITE && self === top` (drop the `self === top` clause only if a tool is declared frame-scoped).
4. **Register**: bootstrap creates `AbortController` per version, registers each tool with `{signal}`, wraps `execute` so calls after dispose throw, reports `registered/loaded/error` through `Runtime.addBinding({name:'__toolsmithReport', executionContextName:'toolsmith'})`, and correlates with `WebMCP.toolsAdded` (source-of-truth that Chromium accepted it; also carries `stackTrace` for attribution).
5. **Verify**: run the Builder's test call through `WebMCP.invokeTool` (never `Runtime.evaluate` of `execute`) so the same path agents will use is what's tested; validate `toolResponded.output` against `contract.output` (Zod in main process); write evidence (KQ6); only then `state.active = version`.
6. **Switch/disable**: evaluate `__toolsmith.dispose()` in the world (→ AbortSignal unregisters, `toolsRemoved` fires), then `removeScriptToEvaluateOnNewDocument` and re-add for the new version, then re-run bootstrap immediately. No page reload needed; a navigation naturally re-runs the new-document script.

### Gaps
- `runImmediately` semantics with `worldName` on an already-created isolated world of the same name (does it create a second world?) — not verified; DeepDeck's approach (explicit `createIsolatedWorld` returning the existing world's context id for a same-named world) is the proven path.
- Electron's `webContents.debugger` (protocol "1.3") exposes experimental commands like `WebMCP.*` — proven by DeepDeck, but Electron's docs on this were not fetched.

## KQ4. Sandbox model, static checks, the frozen `http()` helper, CSP

### Takeaway
An isolated world gives *scope* isolation (separate globals, page can't reach the script's objects, script can't reach page JS objects) and its own CSP, but **no** privilege reduction: it shares the DOM and origin, `fetch` carries the site's cookies, and every DOM/network global is reachable. So the enforceable perimeter for Built tools is (1) build-time lint that rejects raw network/eval globals, (2) a runtime prelude that shadows those globals inside the IIFE and hands the tool a logging `http()` closure, and (3) the app-side gates (approval, allowlist, call log). Freezing globals inside the same world is defence against *accidental* misuse by generated code, not against a determined adversary; CDP-injected scripts are not blocked by page CSP.

### Cited Findings
- Isolated worlds: "renderers inject scripts in an isolated world – a separate v8::Context that is unique to the extension … private execution environment that isn't accessible to the page"; content scripts in isolated worlds "have their own Content Security Policy … when a content script is injected into the main world, the CSP of the page applies" — [Chrome content-scripts docs](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) via search summary; [chromium-isolated-world-csp-demo](https://github.com/hjanuschka/chromium-isolated-world-csp-demo) ("allows eval() in content scripts without weakening page CSP")
- CDP's `Page.createIsolatedWorld` now takes its own `contentSecurityPolicy` string and "If omitted, any existing CSP for the world will be cleared" — i.e. an isolated world's CSP is independent of the page's — [browser_protocol.json](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)
- `Page.setBypassCSP({enabled})` exists ("Enable page Content Security Policy by-passing") but is unnecessary for isolated-world injection and would weaken the page — same
- DeepDeck's agent guidance confirms the practical limit: "page-owned JavaScript globals may not be accessible" and fetches must be tied to `sdk.signal` — [builder-skill.ts](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/builder-skill.ts)
- OpenTabs' helper wraps `fetch` with a timeout and status→error mapping but does not restrict origin — plugins are trusted npm code, gated instead by `ToolPermission = 'off' | 'ask' | 'auto'` per plugin/tool and `reviewedVersion` — [plugin-sdk/src/fetch.ts](https://github.com/opentabs-dev/opentabs/blob/main/platform/plugin-sdk/src/fetch.ts); [shared/src/index.ts L109–119](https://github.com/opentabs-dev/opentabs/blob/main/platform/shared/src/index.ts)
- DeepDeck's compile step already turns two esbuild diagnostics into hard errors (`unsupported-dynamic-import`, `unsupported-require-call`) and blocks all module resolution with an `onResolve` plugin — [webmcp-store.ts L199–209](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-store.ts)
- DeepDeck's CDP proxy policy is an allowlist of methods (`Page.*`, `Runtime.evaluate/callFunctionOn/addBinding`, `WebMCP.enable/disable`…), forces `grantUniveralAccess=false`, and restricts `Page.navigate` to the site's origin and `DOM.setFileInputFiles` to the site workspace — [browser-devtools-policy.ts L30–70](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-devtools-policy.ts)
- The CDP `toolResponded.output` is documented as "untrusted and poses a prompt injection risk" — [browser_protocol.json](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)
- The spec's own security framing: tool outputs may be flagged `untrustedContentHint`; `exposedTo` restricts which same-tree documents see a tool — [index.bs](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)

### Inferences (design)
- **What the isolated world does isolate**: JS scope (page can't enumerate or monkey-patch Toolsmith's objects; Toolsmith code can't be tricked by page-patched `Array.prototype`, `fetch`, etc. — the world has its own pristine built-ins), and CSP (inline IIFE runs on strict-CSP sites; no need for `setBypassCSP`). **What it does not**: origin, cookies/credentials (`fetch`/XHR are same-origin-credentialed by default), DOM (can click "Delete account"), storage (`localStorage`, IndexedDB), `window.open`, `postMessage`. Hence "sandbox" is a misnomer; call it a *scoped runtime*.
- **Static lint list** (fail the build): identifiers `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon`, `Worker`, `SharedWorker`, `ServiceWorker`/`navigator.serviceWorker`, `eval`, `Function`, `import()`/`import.meta`, `document.cookie`, `localStorage`/`sessionStorage`/`indexedDB`, `open`/`window.open`, `postMessage`, `location.assign|replace|href=`, `document.write`, `setTimeout(string)`, `with`, `globalThis`/`window`/`self` used as computed-member bases, `Reflect`/`Proxy` on the ctx object, `crypto.subtle` [optional]. Implementation: run the TypeScript compiler API (`ts.createSourceFile` + a walker over `Identifier`/`PropertyAccessExpression`/`ElementAccessExpression`/`CallExpression`) **before** esbuild — it sees the original source, resolves shadowing by checking the binding chain, and can reject computed access (`window["fe"+"tch"]`) as a class ("no computed member access on globals"). An esbuild `onLoad` plugin can host the same walker but only sees text; ESLint `no-restricted-globals`/`no-restricted-properties` is the fastest to stand up but weaker on computed access. Recommend: TS-API lint as the gate, esbuild `define` to replace banned identifiers with `void 0` as belt-and-braces (`define: { fetch: 'undefined', XMLHttpRequest: 'undefined', ... }` rewrites *free* identifier references only).
- **Runtime prelude (banner)**: wrap the bundle as `(function(ctxFactory){ const fetch=undefined, XMLHttpRequest=undefined, WebSocket=undefined, ... ; /* bundle */ })(__toolsmith.ctx)` so the identifiers are lexically shadowed inside the IIFE; then `Object.freeze` the `ctx` and `ctx.http`. This holds against **generated, linted code** (which cannot name the globals or reach `globalThis`), not against arbitrary code — anything with `globalThis` or `Function` access escapes, which is why those are lint errors and why the world is per-site (there is nothing more valuable in the world than the page already has).
- **`http()` helper** (closure over the real `fetch` captured at prelude time): `http(path | same-origin URL, { method, headers, body, timeoutMs ≤ 30 000, maxBytes ≤ 5 MiB, expect: 'json'|'text'|'html' })`. Rules: reject any URL whose `origin !== location.origin` unless it appears in the version's `contract.network.allow` (origins listed by Builder, reviewed by the user — the Tampermonkey `@connect` idea); always `credentials: 'same-origin'`, never `'include'`; `redirect: 'error'` for cross-origin redirects; strip `Authorization`/`Cookie` from tool-supplied headers; chain the call `AbortSignal` with a timeout; count bytes while streaming and abort at the cap; log `{callId, method, url (query redacted per allowlist), status, bytes, ms}` to the app via the report binding **before** returning; return `{status, headers (allowlisted), body}`. Writes (`method !== GET/HEAD`) are refused unless the version's Trust class is `writes` and the call has an Approval token from the app (passed in through `invokeTool` input under a reserved key, checked in the prelude and removed before the tool sees the input) [design, unverified].
- **CSP**: CDP injection into an isolated world runs regardless of page CSP; but the *page's* `connect-src` still governs network requests made from that world? — In Chromium, requests initiated from an extension isolated world are subject to the extension's CSP, not the page's; for a CDP-created world the `createIsolatedWorld.contentSecurityPolicy` parameter suggests the same model (world CSP, cleared by default). Mark **[unverified for connect-src]**; sites with strict `connect-src` are a test case to include in verification.

### Gaps
- Could not read Chrome's `secure-tools` page or Tampermonkey's docs (proxy-blocked); the `@connect` analogy is from memory **[unverified]**.
- No primary source found confirming that `fetch` from a CDP isolated world ignores the page's `connect-src`.

## KQ5. On-disk store

### Takeaway

### Inferences (Toolsmith layout under `app.getPath('userData')`)
```
Toolsmith/
  sites/<site-host>/                     # human-readable host; also store sha256(origin) in site.json
    site.json                            # { origin, createdAt, webmcp: 'native'|'polyfill'|'disallowed' }
    tools/<name>/
      tool.json                          # { name, site, createdAt, goal, trust: 'read'|'writes',
                                         #   enabled, active, lastGood, versions: [...ids] }
      versions/<sha256-of-bundle>/
        source.ts                        # exactly what Builder wrote
        bundle.js                        # esbuild output (what is injected)
        contract.json                    # name, description, inputSchema (JSON Schema),
                                         #   outputSchema, reads[], writes[], network.allow[],
                                         #   needs ('signed-in'), trustClaim, annotations
        version.json                     # { id, sourceSha256, contractSha256, compiler, target,
                                         #   sdkVersion, createdAt, builder: {provider, model?} }
        evidence/<timestamp>/            # one folder per verification or Re-check (KQ6)
      state.json                         # { active, lastGood, enabled, disabledReason?, updatedAt }
  log/calls.sqlite                       # append-only: tool, version, callId, input hash, ms,
```

- Keep `state.json` separate from `tool.json` (DeepDeck's split): the manifest is written once per version, the state flips often; `lastGood` = the last version whose most recent evidence is `pass`. Rollback = `state.active = <older id>` (never deletes; "Roll back … Never deletes Versions" in `CONTEXT.md`).
- JSON files vs SQLite: files for anything a user might inspect or diff (source, contract, evidence) and for atomic single-writer state; SQLite (`node:sqlite`, no native rebuild) for the call log and Re-check history where queries ("last 30 days of failures for tool X") and append throughput matter. Use `DatabaseSync` in the main process only; keep WAL mode; file lives in userData so it is per-user.
- Concurrency: one process owns the store (the Electron main process); serialise per tool like DeepDeck's `withSite`; the MCP server thread reads `state.json` + `contract.json` and never writes.

## KQ6. Package format for export/import, and the verification-evidence model

### Takeaway
DeepDeck's `WebMCPPackage` (`formatVersion`, `origin`, `entry`, `sourceSha256`, `runtime: {id, sdkVersion}`, `tools[]` directory, `license`, `tags`) plus a GitHub-commit `provenance` record is the nearest precedent for a source-level package; Claude Agent Skills' `SKILL.md` folder shows the "folder with a manifest at root" convention. Toolsmith's `.toolsmith` package should be a zip of exactly one version folder (source, bundle, contract, version.json, evidence) plus a top-level `package.json`-style manifest with content hashes, and the import rule should be DeepDeck's: it lands as a new **off, unverified** version that must pass the same install-and-test gate as a fresh build before it can become active.

### Cited Findings
- DeepDeck package contract: `WebMCPPackage { formatVersion: 1; name; description; version (semver, ≤80 chars); origin (exact public https origin — rejects IPs, `.localhost/.local/.internal`); entry (relative path, ≤8 segments); sourceSha256; runtime: { id: 'deepdeck-webmcp'; sdkVersion: 1 }; license; tools: ≤100 × { name /^[a-zA-Z0-9_-]+$/, description ≤2000, inputSchema.type==='object' }; tags ≤20 }`; duplicate tool names rejected — [webmcp-package.ts L6–21, L71–93](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-package.ts)
- Provenance: `GitHubSource { author?, repositoryId, repository (https://github.com/owner/repo only), manifestPath, commit (40-hex), release?, releaseUrl?, version, sourceSha256 }`; on build the store checks `provenance.sourceSha256 === sha256(source)` ("Imported source digest mismatch") and bakes provenance into the revision id — [webmcp-package.ts L94–106](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-package.ts); [webmcp-store.ts L191–194, L70–72](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-store.ts)
- Import never touches the draft: "An imported source is compiled in isolation; it never overwrites the editable draft", and activation still requires a live install receipt — [webmcp-store.ts L186](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-store.ts)
- `exportRevision` re-verifies `sha256(source.ts) === manifest.sourceDigest` before returning `{source, revision, sourceDigest, compiler, provenance?, upstream?}` — [webmcp-store.ts L254–262](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/webmcp-store.ts)
- OpenTabs distributes plugins as npm packages (`opentabs-plugin` keyword, `OpenTabsPlugin` default export, `urlPatterns` as Chrome match patterns) and gates them locally with `reviewedVersion` per plugin plus `off|ask|auto` permissions — [plugin-sdk/package.json](https://github.com/opentabs-dev/opentabs/blob/main/platform/plugin-sdk/package.json); [shared/src/index.ts](https://github.com/opentabs-dev/opentabs/blob/main/platform/shared/src/index.ts)
- Agent Skills spec: a skill "is a directory containing, at minimum, a `SKILL.md` file" with optional `scripts/`, `references/`, `assets/`; frontmatter `name` (1–64 chars, lowercase alnum + hyphens), `description` (≤1024), `compatibility` (≤500), `allowed-tools` (experimental) — [agentskills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx)
- WebMCP annotations available to carry trust in the package: `readOnlyHint`, `consequentialHint`, `untrustedContentHint` — [index.bs](https://github.com/webmachinelearning/webmcp/blob/main/index.bs)
- DeepDeck's install receipt is `{ installed:true, origin, revision, matched, registered, failed, tabs: [{tabId, documentId, revision, registered[], tools[]}] }`, and its post-activate message is "Call the new tools and verify their real results before claiming the task is complete" — registration is proven, function is not — [native-contract.d.ts](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/native-contract.d.ts); [runtime.ts L445](https://github.com/jo32/DeepDeck/blob/main/plugins/browser/src/runtime.ts)
- DeepDeck's page inspection snapshot collects `content {title,url,text,elements}`, `accessibility`, `frames`, `console`, `tools`, and `Page.captureScreenshot({format:'png', fromSurface:true})`; it also keeps the last 150 `Network.requestWillBeSent/responseReceived` entries per tab — raw material for evidence — [browser-window.ts L1008–1016, L293–301](https://github.com/jo32/DeepDeck/blob/main/apps/desktop/src/main/windows/browser-window.ts)
- Tool results are untrusted content per CDP — [browser_protocol.json](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)

### Inferences (package format)
- `.toolsmith` = zip (not a bare folder: one file to email/AirDrop) containing:
  ```
  manifest.json      { formatVersion:1, kind:'toolsmith-tool', name:'toolsmith.<site>.<name>',
                       site:'https://github.com', goal, trustClaim, sdkVersion, compiler, target,
                       versionId (= sha256 of bundle.js), files:{ 'source.ts':sha256, 'bundle.js':sha256,
                       'contract.json':sha256, 'evidence/...':sha256 }, createdAt, exportedBy:{app, appVersion} }
  source.ts  bundle.js  contract.json  version.json  evidence/<ts>/…  README.md (rendered Contract)
  ```
  plus an optional `signature.json` (Ed25519 over `manifest.json`, key stored in the macOS Keychain) so a recipient can see "signed by <name>"; hashes alone protect integrity, the signature protects attribution. Signing is optional in v1; hashing is mandatory.
- **Import rule** ("arrives off and unverified"): verify every hash → recompile `source.ts` with the pinned compiler and require `sha256(recompiled) === versionId` (reject packages whose bundle doesn't reproduce; the bundled `bundle.js` is only a convenience) → create `versions/<id>/` with imported evidence moved to `evidence/imported/` (kept as history, never counted as *current* verification) → `state.enabled=false`, `active` unchanged → prompt the user to Verify. Trust class resets to `writes` (glossary default) regardless of the package's `trustClaim`.
- Precedent mapping: Tampermonkey's `@match` ≈ `site` (one origin, not a pattern); `@grant`/`@connect` ≈ `contract.network.allow` + `ctx` surface; `@version`/`@updateURL` ≈ `versionId` + optional `provenance` **[Tampermonkey semantics from memory, unverified]**. OpenTabs npm packages ≈ a registry Toolsmith deliberately does not have in v1. Agent Skills ≈ the "folder with a root manifest + README that a human reads first" shape.

### Inferences (evidence model)
- Per verification run, `evidence/<ISO-ts>/run.json`:
  `{ versionId, kind:'verify'|'recheck', trigger:'builder'|'user'|'nightly', startedAt, ms, url, documentId, frameId, input, inputValid, output (capped 64 KiB, with a note if truncated), outputSha256, outputSchemaValid, invocation:{status, errorText?}, http:[{method,url,status,bytes,ms}], dom:{ touched:[{selector, role, textSha256, outerHTMLSha256}] }, console:[…], toolsAddedSeen:true, annotations, verdict:'pass'|'fail', reason? }`
  plus `screenshot.png` (only when the tool is `writes` or the user opted in — screenshots can contain PII; the glossary asks Toolsmith to minimise data held) and `before.json/after.json` DOM fingerprints for `writes` tools.
- **DOM fingerprint**: for each selector the tool touched (recorded by `ctx.dom` at call time) store role/name from the accessibility tree plus hashes of text and outerHTML; for `http()` store the response's top-level JSON key set and array lengths (a "shape hash"), not bodies. Drift = same input → (a) invocation error, (b) `outputSchemaValid=false`, (c) output shape hash changed while `contract.output` says it should not, (d) a touched selector no longer resolves, or (e) an HTTP endpoint changes status class (2xx→4xx). Any of these fails the Re-check.
- **Nightly Re-check**: only versions whose Trust class is `read` and whose `contract.needs` is satisfiable (site open and, if `signed-in`, an active session detected by a Builder-authored `isReady`-style probe like OpenTabs'); run the stored verification input through `WebMCP.invokeTool`; on fail set `enabled=false, disabledReason='recheck-failed:<reason>'` and keep `lastGood` unchanged ("A failed Re-check turns the tool off; it never edits the tool"). `writes` tools are never re-checked automatically; they show "last verified <date>".

### Gaps
- No public precedent found for machine-readable verification evidence attached to browser tools; the evidence schema above is a proposal.
- Whether a screenshot should be stored by default is a product/privacy call, not settled by any source read.

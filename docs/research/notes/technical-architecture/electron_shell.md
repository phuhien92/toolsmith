# Toolsmith — Electron shell architecture (as of 2026-09-23)

Scope: the Electron/React/TypeScript shell for a macOS workshop app that embeds untrusted, logged-in sites in a built-in Chromium, reads their WebMCP tools over the CDP `WebMCP` domain, injects generated tool code, and runs a local MCP server. Chat UI is out of scope (Inspect / Build / Serve panels only).

Evidence sources used: the npm registry (versions, publish dates), the Electron repo at tag `v44.4.4` (DEPS and `docs/`), the Chromium GitHub mirror at tag `152.0.7977.130` (the exact Chromium in Electron 44.4.4), the `ChromeDevTools/devtools-protocol` clone (package `0.0.1702366`, commit 2026-09-22), the local DeepDeck clone (`apps/desktop/src/main/windows/*`), and the WebMCP spec repo. Local-clone citations are given as repo paths; every remote fact has a URL.

## KQ1. Which Electron to pin, what Chromium/Node it carries, and whether WebMCP (CDP domain + `document.modelContext`) is in that Chromium

### Takeaway
Pin **Electron 44.4.4** (npm `latest`, published 2026-09-22): Chromium **152.0.7977.130**, Node **v24.21.0**. That Chromium tag contains both the `WebMCP` CDP domain (`domains/WebMCP.pdl`) and the `document.modelContext` IDL, gated by the Blink runtime feature **`WebMCP`** (`status: "experimental"`, origin-trial feature). Electron 45 is still alpha (`45.0.0-alpha.10`); there is no Electron 46 on the registry.

The Electron pin must be treated as "this specific Chromium"; each Electron major bump (new Chromium) should be gated on re-running a WebMCP smoke test, because the domain is marked `experimental domain` and the tip PDL already differs from the 152 one (see KQ4).

## KQ2. How to enable WebMCP for every embedded site — exact switches and Blink feature names

### Takeaway
Set `webPreferences.enableBlinkFeatures: 'WebMCP'` on every **site** `WebContentsView` (this is exactly what DeepDeck ships and is the mechanism Electron documents against `runtime_enabled_features.json5`). Do **not** put it on the app-UI view. `--enable-features=WebMCP` (base::Feature override) or `--enable-experimental-web-platform-features` are process-wide alternatives; `WebMCPTesting` is a separate Blink feature that *implies* `WebMCP` and is what Chrome's `enable-webmcp-testing` flag is named after, but the flag itself toggles the `WebMCP` base feature.

### Cited Findings
- Electron `webPreferences.enableBlinkFeatures` — "A list of feature strings separated by `,`, like `CSSVariables,KeyboardEventKey` to enable. The full list of supported feature strings can be found in the RuntimeEnabledFeatures.json5 file." `disableBlinkFeatures` is the inverse — [web-preferences.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/structures/web-preferences.md)
- DeepDeck's guest (site) preferences: `{ session: profile, contextIsolation: true, nodeIntegration: false, sandbox: true, ...(webmcpEnabled ? { enableBlinkFeatures: "WebMCP" } : { disableBlinkFeatures: "WebMCP" }), navigateOnDragDrop: false, spellcheck: true, plugins: true }`, applied only to tab views, never to the shell view — `DeepDeck/apps/desktop/src/main/windows/browser-window.ts` lines 85–90.
- Blink status semantics: features with `status: "experimental"` are enabled by `--enable-experimental-web-platform-features` ("works in all Chromium channels"); `status: "test"` features are enabled only under `--run-web-tests` / `--enable-blink-test-features` — [RuntimeEnabledFeatures.md @ 152.0.7977.130](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/third_party/blink/renderer/platform/RuntimeEnabledFeatures.md)
- Origin-trial pattern semantics: with `base_feature_status: "enabled"` + `copied_from_base_feature_if: "overridden"`, the `base::Feature` is enabled by default but its state is **not** copied to the Blink feature unless the base feature is explicitly overridden (e.g. `--enable-features=WebMCP` / `--disable-features=WebMCP`), which then force-enables/disables the Blink feature — same source, "Origin Trial Features and base::Feature" section.
- `implied_by`: "this feature is enabled automatically if any of the implied_by features is enabled" — so enabling `WebMCPTesting`, `WebMCPFormAssociatedCustomElements` or `WebMCPDeclarativeFileInput` also turns on `WebMCP` — same source.
- Chrome's flag `enable-webmcp-testing` is wired to `FEATURE_VALUE_TYPE(blink::features::kWebMCP)` (about_flags.cc ~line 12931), i.e. it overrides the **`WebMCP`** base feature, not `WebMCPTesting` — [about_flags.cc @ 152.0.7977.130](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/chrome/browser/about_flags.cc)
- Electron's command-line switches must be appended via `app.commandLine.appendSwitch(...)` before the `ready` event — [command-line-switches.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/command-line-switches.md)
- Electron's security checklist item 10 is "Do not use `enableBlinkFeatures`" (and item 9 "Do not enable experimental features") — local `scratchpad/el/docs/tutorial/security.md` at v44.4.4, headings at lines 450 and 484; same file upstream: [security.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/tutorial/security.md)
- `document.modelContext` is `[SecureContext]` — only `https:` (and localhost) pages get it — [model_context_supplement.idl](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/third_party/blink/renderer/core/script_tools/model_context_supplement.idl)

### Inferences
- Recommended concrete setup (scoped, not process-wide):
  ```ts
  const siteSession = session.fromPartition('persist:sites');
  const sitePrefs: Electron.WebPreferences = {
    session: siteSession, sandbox: true, contextIsolation: true, nodeIntegration: false,
    enableBlinkFeatures: 'WebMCP',            // exact Blink name at Chromium 152
    navigateOnDragDrop: false,
  };
  ```
  This satisfies the security checklist's *intent* (the flag reaches only site renderers, and the app-UI renderer never has it). Note that the checklist wording is against `enableBlinkFeatures` generally, so the deviation should be documented in the repo.
- If a site's declarative tools rely on form-associated custom elements, add `WebMCPFormAssociatedCustomElements` to the same comma-separated string; it is `experimental` in 152 and implies `WebMCP`. Leave `WebMCPDeclarativeFileInput` off (`status: "test"`).
- A process-wide `app.commandLine.appendSwitch('enable-features', 'WebMCP')` is an acceptable belt-and-braces addition (it flips the base feature to "overridden", which forces the Blink feature on everywhere including the app UI); prefer the per-view `enableBlinkFeatures` so the app UI does not carry an experimental API surface.
- Because the Blink feature is per-renderer, an `about:blank` or `http://` page will not expose `document.modelContext` (SecureContext); the Inspect panel should show "not a secure context" rather than "no tools".

### Gaps
- I could not find the source of the `WebMCPTesting` Blink feature's actual effect (the `modules/webmcp` directory guessed at the tag returned 404). Treat "what `WebMCPTesting` adds beyond `WebMCP`" as unverified; DeepDeck gets by with `WebMCP` alone.
- Not verified empirically that `enableBlinkFeatures: 'WebMCP'` is sufficient for `WebMCP.enable` to succeed in Electron 44.4.4; the evidence is DeepDeck doing exactly this on Electron 43.4.0 (Chromium 150) plus the DevTools gate being `ENABLED_BY_DEFAULT` in 152. A one-line smoke test on first scaffold is warranted.

## KQ3. Window structure: `BaseWindow` + `WebContentsView` layout, right-hand React panel, macOS title bar, vibrancy, drag regions — and what to copy from DeepDeck

### Takeaway
Use one `BaseWindow` with a full-window app-UI `WebContentsView` (React) as the bottom layer and one `WebContentsView` per site tab positioned with `setBounds` into the "browser" rectangle; the React chrome (tab strip + right Inspect/Build/Serve panel) simply renders around the hole. DeepDeck's `browser-window.ts` is a proven template for this, including `titleBarStyle: 'hiddenInset'` and `trafficLightPosition`.

### Cited Findings
- `BaseWindow` is documented as the container for multiple `WebContentsView`s: `win.contentView.addChildView(leftView)` / `rightView`, each positioned via `view.setBounds({x,y,width,height})`; the doc also shows `win.on('closed', () => view.webContents.close())` — [base-window.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/base-window.md); [web-contents-view.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/web-contents-view.md)
- `BaseWindow` options: `titleBarStyle` (`default` | `hidden` | `hiddenInset` macOS "traffic light buttons slightly more inset"); `trafficLightPosition` (Point, macOS, "custom position for the traffic light buttons in frameless windows"); `titleBarOverlay` (enables the Window Controls Overlay JS/CSS env vars; `height` option); `vibrancy` (macOS: `appearance-based`, `titlebar`, `selection`, `menu`, `popover`, `sidebar`, `header`, `sheet`, `window`, `hud`, `fullscreen-ui`, `tooltip`, `content`, `under-window`, `under-page`) with `visualEffectState` (`followWindow` | `active` | `inactive`); `roundedCorners`; `win.setVibrancy(type | null)` — [base-window-options.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/structures/base-window-options.md); [base-window.md](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/base-window.md)
- Drag regions: the custom-title-bar tutorial tells the renderer to mark the draggable strip with the CSS `app-region: drag` — local `scratchpad/el/docs/tutorial/custom-title-bar.md` (v44.4.4), line 55; upstream: [custom-title-bar.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/tutorial/custom-title-bar.md)
- DeepDeck window creation (copy this shape): `new BaseWindow({ width: 1440, height: 940, minWidth: 900, minHeight: 600, ...(process.platform === 'darwin' ? { titleBarStyle: 'hiddenInset', trafficLightPosition: { x: 18, y: 17 } } : {}), title, backgroundColor: "#f8fafc", show: false, autoHideMenuBar: true })`; then `shell = new WebContentsView({ webPreferences: { contextIsolation: true, nodeIntegration: false, sandbox: true } }); window.contentView.addChildView(shell)`; `window.on("resize", syncBounds)` — `DeepDeck/apps/desktop/src/main/windows/browser-window.ts` lines 707–735.
- DeepDeck layout: the shell view is always full-size (`shell.setBounds({x:0,y:0,width,height})`), and each tab view gets `browserContentBounds(width, height, top, right)` where `top = 92` (tab strip + address bar height) and `right` is the width of the side panel; HTML-fullscreen sets both to 0 — same file, lines 55–60 and 123–130. Tabs are `new WebContentsView({ webPreferences: { ...options.webPreferences, ...guestPreferences } })` added with `window.contentView.addChildView(view)` (lines 357–380) and removed with `window.contentView.removeChildView(tab.view)` (line 693).
- DeepDeck keeps the app shell and sites in separate `WebContentsView`s so the site never has "the shell's session nor an opener to it"; `target=_blank` links inside the shell are turned into managed site tabs via `shell.webContents.setWindowOpenHandler(... return { action: "deny" })` and `will-navigate` is cancelled unless same-origin as the shell — same file, lines 714–733.

### Inferences
- Recommended structure for Toolsmith:
  - `BaseWindow` (macOS: `titleBarStyle: 'hiddenInset'`, `trafficLightPosition: {x: 18, y: 17}`, `vibrancy: 'sidebar'` optional, `backgroundColor` set to avoid flashes, `show: false` until React is ready).
  - `uiView: WebContentsView` — the React app, bounds = full content size; renders tab strip (top ~92 px like DeepDeck), address bar, and the right-hand Inspect/Build/Serve panel; draggable title strip uses `app-region: drag` and `no-drag` on interactive controls.
  - `siteViews: Map<tabId, WebContentsView>` — one per tab, bounds = `{x: 0, y: top, width: W - panelWidth, height: H - top}`; only the active tab is added/visible (DeepDeck adds all and positions the active one; `view.setVisible(false)` is the WebContentsView way to hide others).
  - Because native views are always on top of the UI view, popovers/modals in React that must overlap the site area need the site view shrunk or hidden while open (DeepDeck tracks `modalOpen` and recomputes bounds for exactly this reason).
- Vibrancy: use it on the window and let the React panel/tab strip be transparent for a native sidebar look; site views are opaque anyway. Keep it optional — it costs GPU compositing and DeepDeck does not use it.

### Gaps
- `View.setVisible` and `WebContentsView` extra options (e.g. `setBorderRadius`) were not verified in the v44.4.4 `view.md` (not downloaded); the `web-contents-view.md` at that tag documents only the constructor, `webContents` property and the two-view example.

## KQ4. CDP from Electron: attach, one client per target, DevTools interaction, `WebMCP` events, script injection into an isolated world, `Runtime.evaluate`, frames/OOPIFs, `Page.enable` cost

### Takeaway
`webContents.debugger.attach('1.3')` once per site `WebContentsView`, then `Page.enable`, `Runtime.enable`, `Runtime.addBinding({name, executionContextName: WORLD})`, `Page.addScriptToEvaluateOnNewDocument({source, worldName: WORLD})`, `Page.getFrameTree`, and finally `WebMCP.enable` (which replays `toolsAdded` for every existing tool). Filter `message` events to `sessionId === undefined` so child sessions don't get folded in. DeepDeck's `browser-window.ts` lines 236–346 and `browser-webmcp-script.ts` are the reference implementation and are worth copying almost verbatim.

### Cited Findings
- Electron `Debugger`: `attach([protocolVersion])`, `isAttached()`, `detach()`, `sendCommand(method[, params, sessionId])` → Promise; `message` event carries `(event, method, params, sessionId)`; the `detach` event "happens either when `webContents` is closed or DevTools is invoked for the attached `webContents`"; a `sendCommand` issued right after `attach()` "may not resolve until navigation occurs"; commands with no result resolve to `{}` — [debugger.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/debugger.md)
- CDP `WebMCP` domain at Chromium 152.0.7977.130 (`experimental domain WebMCP`, `depends on Runtime, Page, DOM`):
  - commands: `enable` ("Enabling the domain will trigger a toolsAdded event for all currently registered tools"), `disable`, `invokeTool(frameId: Page.FrameId, toolName: string, input: object) → { invocationId: string }` ("Response is sent before tool events"), `cancelInvocation(invocationId)`;
  - events: `toolsAdded { tools: Tool[] }`, `toolsRemoved { tools: RemovedTool[] }` (`{name, frameId}`), `toolInvoked { toolName, frameId, invocationId, input: string }`, `toolResponded { invocationId, status: Completed|Canceled|Error, output?: any, errorText?: string, exception?: Runtime.RemoteObject }` with the note "The output is untrusted and poses a prompt injection risk";
  - `Tool { name, description, inputSchema?: object, annotations?: Annotation, frameId: Page.FrameId, backendNodeId?: DOM.BackendNodeId, stackTrace?: Runtime.StackTrace }`; `Annotation { readOnly?, untrustedContent?, autosubmit? }` at the 152 tag — [WebMCP.pdl @ 152.0.7977.130](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/third_party/blink/public/devtools_protocol/domains/WebMCP.pdl)
  - The protocol tip (devtools-protocol `0.0.1702366`, 2026-09-22) adds two `Annotation` hints not in 152: `consequential` and `debugging` — local `scratchpad/devtools-protocol/pdl/domains/WebMCP.pdl` diffed against the 152 file; [devtools-protocol repo](https://github.com/ChromeDevTools/devtools-protocol)
- `Page.addScriptToEvaluateOnNewDocument(source, worldName?, includeCommandLineAPI?, runImmediately?)` → `identifier`; `worldName` "creates an isolated world with the given name and evaluates given script in it. This world name will be used as the ExecutionContextDescription::name"; `runImmediately` "runs the script immediately on existing execution contexts or worlds. Default: false" (all three experimental) — local `scratchpad/devtools-protocol/pdl/domains/Page.pdl` lines 563–578; [Page domain](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-addScriptToEvaluateOnNewDocument)
- `Page.createIsolatedWorld(frameId, worldName?, grantUniveralAccess?)` (sic, misspelled in the protocol) — same file lines 632–640. `Target.setAutoAttach(autoAttach, waitForDebuggerOnStart, flatten?, filter?)`; `Target.autoAttachRelated` is "Only available at the Browser target" — `scratchpad/devtools-protocol/pdl/domains/Target.pdl` lines 237–255.
- DeepDeck initialisation sequence (`initialize()`): `wc.debugger.attach("1.3")` → `Page.enable` → `Runtime.enable` → `Network.enable` → `Runtime.addBinding({ name: WEBMCP_BINDING, executionContextName: WEBMCP_WORLD })` → `Page.getFrameTree` (walk it to record `mainFrameId` and each frame's origin/parent) → for each installed generated script `Page.addScriptToEvaluateOnNewDocument({ source: webmcpBootstrap(script), worldName: WEBMCP_WORLD })` (removing the previous identifier first) → `WebMCP.enable` wrapped in try/catch that records `webmcpError = "WebMCP discovery is unavailable: …"` → if the tab was not blank, immediately run the bootstrap once via `evaluate(tab, source, true)` because "a popup may have started loading before its protocol session was attached" — `DeepDeck/apps/desktop/src/main/windows/browser-window.ts` lines 322–352.
- DeepDeck `evaluate(tab, expression, isolated)`: `Page.createIsolatedWorld({ frameId: mainFrameId, worldName })` → `Runtime.evaluate({ expression, awaitPromise: true, returnByValue: true, contextId, timeout: 15_000 })`, throwing on `exceptionDetails` — same file lines 308–320.
- DeepDeck event routing: `wc.debugger.on("message", (_e, method, params, sessionId) => { if (!sessionId) handleProtocol(...) })` with the comment "DevTools MCP owns separate CDP sessions on this same WebContents. Their events must not be folded twice"; `debugger.on("detach")` is handled in `setImmediate` and, if still detached, marks the tab "Browser protocol disconnected: … Reload this tab to reconnect" and cancels in-flight calls — lines 365–376. `send()` awaits a `setImmediate` tick after a rejected `sendCommand` because "Electron rejects pending CDP commands from inside WebContents destruction" — lines 149–159.
- DeepDeck frame bookkeeping: `Page.frameNavigated` (main frame → `mainFrameId`; subframe → invalidate that subtree), `Page.frameDetached` (recursively drop child frames — "CDP can detach a whole frame subtree without a separate event per descendant"), `Page.navigatedWithinDocument`, `Runtime.executionContextCreated` (map `context.id → auxData.frameId` when `context.name === WEBMCP_WORLD`), `executionContextDestroyed`, `executionContextsCleared` — lines 184–262.
- DeepDeck `WebMCP.toolsAdded` handling keys tools by `(frameId, name)`, tags a tool `source: "deepdeck"` if its name was registered by a generated script (tracked through the `Runtime.bindingCalled` report), else `"site"`; `toolsRemoved` deletes by the same key; `WebMCP.toolResponded` resolves the pending call, and an `earlyResponses` buffer handles a `toolResponded` arriving before the `invokeTool` promise returns its `invocationId` — lines 276–305 and 218–230.
- DeepDeck `webmcp.call`: verifies the tool's `documentId`/`revision` are still current, registers a 60 s timeout that sends `WebMCP.cancelInvocation`, then `WebMCP.invokeTool({ frameId, toolName, input })` — lines 993–1012.
- DeepDeck's injected bootstrap (`browser-webmcp-script.ts`) runs **only in the isolated world**, bails unless `location.origin === script.origin && self === top`, reads `document.modelContext` (throws "WebMCP is unavailable or disabled by this site" if absent), wraps `context.registerTool({...tool, name: 'deepdeck_' + name, execute}, { signal })`, reports `registered`/`loaded`/`error` back to main via the `Runtime.addBinding` function, and supports `dispose()` via `AbortController` — `DeepDeck/apps/desktop/src/main/windows/browser-webmcp-script.ts` (69 lines). Disposal on uninstall runs `webmcpDispose(origin)` through `evaluate(..., true)` and `Page.removeScriptToEvaluateOnNewDocument` — `browser-window.ts` lines 980–990.
- DeepDeck's DevTools-lease policy strips `grantUniveralAccess` from any client `Page.createIsolatedWorld` ("Puppeteer requests this by default … remove the extra authority") and allows only an allow-list of CDP methods including `WebMCP.enable/disable` but *not* `WebMCP.invokeTool` ("all invocations go through Browser's versioned API") — `browser-devtools-policy.ts` lines 30–60.
- The DeepDeck "tab.devtools" command calls `wc.openDevTools({ mode: 'detach' })` — `browser-window.ts` line 954.

### Inferences
- One `debugger` client per site `WebContentsView` is the correct unit; Electron's `Debugger` is bound to the WebContents, and `sessionId` support means child targets (via `Target.setAutoAttach({autoAttach: true, waitForDebuggerOnStart: false, flatten: true})`) can be multiplexed over the same client if OOPIF coverage is ever needed. DeepDeck does *not* auto-attach; it relies on `WebMCP.toolsAdded` carrying `frameId` and on `Page.getFrameTree`/`frameNavigated` for origin lookup, which implies the `WebMCP` domain on the page session already reports tools from all frames of that page. Treat cross-process-iframe coverage as unverified (Gaps).
- DevTools: per the v44.4.4 doc, opening DevTools on a debugger-attached WebContents fires `detach`. DeepDeck accepts that ("Reload this tab to reconnect"). For Toolsmith, either (a) never open DevTools on site views (use the panel's own Inspect data), or (b) on `devtools-closed` re-run `initialize()` (re-attach + `WebMCP.enable`, which replays `toolsAdded`, so state recovers cheaply).
- `Page.enable`/`Runtime.enable`/`Network.enable` are cheap on their own; the real cost is `Network.enable` event volume (DeepDeck caps its ring buffers at 150 requests / 30 console entries). For Toolsmith's Inspect panel, keep `Network.enable` off by default and turn it on only during a Build session.
- The injected bootstrap pattern (isolated world + `Runtime.addBinding` + `AbortController`) is the right way to inject *built* tools: the site's page world cannot see or tamper with the injected code, while `document.modelContext` is the same DOM object so registrations are visible to the `WebMCP` domain. Namespace built tools (`toolsmith.<site>.<name>`, matching Toolsmith's glossary in `scratchpad/toolsmith/CONTEXT.md`) exactly as DeepDeck prefixes `deepdeck_`, and use `runImmediately: true` on `addScriptToEvaluateOnNewDocument` instead of DeepDeck's separate "evaluate once now" step.
- Because `toolResponded.output` is flagged as a prompt-injection risk by the protocol itself, the local MCP server should pass tool output through as `untrusted` content and never let it steer the Builder.

### Gaps
- Whether `WebMCP.toolsAdded` on a page-level session includes tools registered in out-of-process iframes without `Target.setAutoAttach` is not stated in the PDL and I found no test or doc for it. DeepDeck's design (tracking `frameId` without auto-attach) suggests yes for same-process frames at least; verify with a cross-origin iframe fixture.
- The exact Electron 44 behaviour of `debugger` + DevTools coexistence is only documented as "detach on DevTools open"; DeepDeck opens DevTools detached anyway and tolerates the detach. Not empirically re-verified on 44.4.4.

## KQ5. Isolation: sessions, `sandbox`/`contextIsolation`/`nodeIntegration`, permission handlers, `setWindowOpenHandler`, blocking `data:`/`blob:`/`javascript:`/`file:`, `will-navigate`, and whether site views need a preload

### Takeaway
Site views: `session.fromPartition('persist:sites')` (separate from the app UI's session), `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, **no preload** — DeepDeck only attaches a preload to site views for its optional passkey bridge and does everything else over CDP. Gate navigation with `will-navigate` / `will-redirect` to `http:`/`https:` (+`blob:` for same-origin downloads), route `window.open` through `setWindowOpenHandler` into a new managed tab that reuses the same site preferences, and install `setPermissionRequestHandler` + `setPermissionCheckHandler` on the site session.

### Cited Findings
- Electron defaults at v44.4.4: `sandbox` "Default is `true` since Electron 20"; `contextIsolation` "Defaults to `true`"; `nodeIntegration` default `false`; `webviewTag` default `false`; `partition` `persist:` prefix gives a persistent session shared by pages with the same string, otherwise in-memory; `session` object takes precedence over `partition`; `navigateOnDragDrop` default `false`; `additionalArguments` appends to renderer `process.argv` for preloads — [web-preferences.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/structures/web-preferences.md)
- `session.fromPartition(partition[, options])` returns the existing `Session` for that string or creates one; `{cache}` option — [session.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/session.md)
- `ses.setPermissionRequestHandler(handler | null)`: `(webContents, permission, callback, details)`; "if the request comes from a subframe you should use `requestingUrl`"; Electron "forwards every permission type that Chromium requests" (list includes `clipboard-read`, `clipboard-sanitized-write`, `media`, `notifications`, `geolocation`, etc.). `ses.setPermissionCheckHandler(handler | null)`: `(webContents | null, permission, requestingOrigin, details)` returning boolean; `webContents` is `null` for service-worker / notification checks — same file, lines 958–1045.
- `contents.setWindowOpenHandler(handler)` receives `{ url (resolved), frameName, features, disposition, referrer, postBody }` and returns a `WindowOpenHandlerResponse` (`{action: 'deny'}` or `{action: 'allow', overrideBrowserWindowOptions?, createWindow?}`); `will-navigate` / `will-frame-navigate` / `will-redirect` are cancellable and "do not fire for same document navigations"; `devtools-opened` / `devtools-closed` events exist — [web-contents.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/web-contents.md)
- Electron security checklist (v44.4.4) headings: 1 only load secure content; 2 no Node integration for remote content; 3 context isolation; 4 process sandboxing; 5 handle session permission requests from remote content; 6 don't disable `webSecurity`; 7 CSP; 8 no `allowRunningInsecureContent`; 9 no experimental features; 10 no `enableBlinkFeatures`; 11/12 WebView rules; 13 disable or limit navigation; 14 disable or limit creation of new windows; 15 no `shell.openExternal` with untrusted content; 16 current Electron; 17 validate the `sender` of all IPC messages; 18 avoid `file://`, prefer custom protocols; 19 fuses; 20 don't expose Electron APIs to untrusted content — local `scratchpad/el/docs/tutorial/security.md`; [security.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/tutorial/security.md)
- Electron 44 breaking change: "preload scripts only run in DevTools extension frames hosted by DevTools" — [breaking-changes.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/breaking-changes.md)
- DeepDeck: `const profile = session.fromPartition("persist:deepdeck-browser")` for all site tabs; the shell view uses the default session with no preload — `browser-window.ts` lines 85, 710. Site preload is attached only if a Chrome passkey bridge is found (`...(chromePasskeys ? { preload: '../../preload/browser-passkey.cjs' } : {})`), i.e. the base case is **no preload** — line 89.
- DeepDeck URL policy: `browserOrigin()` accepts only `http:`, `https:`, `blob:` with a non-`null` origin; `blob:` handled specially — `browser-policy.ts` lines 25–36. `wc.on("will-navigate")` calls `guestUrl(url)` and on failure `event.preventDefault()` then offers "Open in another application?" only for `mailto:`/`tel:`/`sms:`/`zoommtg:`/`feishu:`/`lark:` via a dialog before `shell.openExternal` — `browser-window.ts` lines 96–106, 382. `will-redirect` off-policy → `preventDefault()` — line 383.
- DeepDeck `setWindowOpenHandler` on site views: deny (with the external-app prompt) unless `guestUrl` passes; otherwise `{ action: "allow", overrideBrowserWindowOptions: { webPreferences: guestPreferences }, createWindow: options => createTab(!options.webContents, options, disposition !== "background-tab") }` — "Adopt that exact instance; replacing it throws in openGuestWindow" — lines 488–500.
- DeepDeck permission model: `setPermissionCheckHandler` and `setPermissionRequestHandler` on the site session; an `automatic` allow-set, a `promptable` set, everything else denied; prompts via `dialog.showMessageBox` keyed by `(topOrigin, requestingOrigin, kind)` with a "remember" checkbox persisted to `userData`; handlers set to `null` on dispose — `browser-session.ts` lines 25–90, 189.
- Spec-level isolation: WebMCP tools are only exposed to same-origin documents unless `exposedTo` lists other origins — [model_context.idl](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/third_party/blink/renderer/core/script_tools/model_context.idl)

### Inferences
- Concrete recommendation:
  - **Two sessions**: default session for the app UI (loads the bundled React app from a custom `app://` protocol or `file://` in dev — checklist #18 prefers a custom protocol); `persist:sites` for every site view. Never share cookies between them.
  - **Site view prefs**: `{ session, sandbox: true, contextIsolation: true, nodeIntegration: false, enableBlinkFeatures: 'WebMCP', navigateOnDragDrop: false }`, no `preload`. Everything Toolsmith needs (tool discovery, invocation, injection, screenshots, DOM inspection for the Builder) is available via CDP, so a site preload adds attack surface for no benefit — and Electron 44's preload semantics changed anyway.
  - **Navigation policy** (checklist #13/#14): allow only `http:`/`https:` (and `blob:` from the same origin, for downloads); `preventDefault()` everything else in `will-navigate`, `will-frame-navigate` (subframes) and `will-redirect`; `setWindowOpenHandler` → new managed tab with the same site prefs, or `deny`. This blocks `data:`, `javascript:`, `file:` and `about:` navigations by construction; `javascript:` typed into the address bar must be rejected by the address-bar parser, not just by Electron.
  - **Permissions** (#5): copy DeepDeck's two-handler pattern; default-deny; prompt for `media`, `notifications`, `geolocation`, `clipboard-read`; auto-allow only `fullscreen` and `pointerLock`-style benign ones.
  - **App UI view**: sandboxed, context-isolated, with a preload that exposes a typed `contextBridge` API (see KQ6); validate `event.senderFrame`/`sender` on every `ipcMain.handle` (checklist #17) so a site view can never reach the IPC surface even if a bug added a preload to it.
- Because the WebMCP `exposedTo` default is same-origin only, injected built tools registered from the isolated world are registered *by* the top document (same origin) and are therefore visible to the domain; nothing extra is needed for the common single-document case.

### Gaps
- No Electron doc at v44.4.4 was found that states explicitly whether `sandbox: true` views with a `worldName` script injected via CDP can call `document.modelContext` (an isolated world's `document` wrapper); DeepDeck's shipped bootstrap does exactly this in a sandboxed view, so it works on Chromium 150; re-verify on 152.

## KQ7. Secrets and storage: `safeStorage` async API, `userData` layout, `node:sqlite` vs `better-sqlite3` vs JSON

### Takeaway
Use `safeStorage.encryptStringAsync`/`decryptStringAsync` (Electron recommends the async API and says the sync one "may be deprecated in a future version"; the v44.4.4 breaking-changes file has **no** entry removing it, so "Electron 46 removes sync" is unverified). Store the tool store in `app.getPath('userData')`; Node v24.21.0's `node:sqlite` is Stability 1.2 (release candidate), which makes it a reasonable v1 choice over `better-sqlite3` **if** Electron's bundled Node exposes it (not verified).

### Cited Findings
- `safeStorage`: "We recommend using the asynchronous API (`encryptStringAsync`/`decryptStringAsync`) over the synchronous API. The async API is non-blocking, supports key rotation, and handles temporary unavailability gracefully. The synchronous API may be deprecated in a future version of Electron." macOS keys live in Keychain Access "in a way that prevents other applications from loading them"; on macOS "access to the system Keychain is required and these calls can block the current thread to collect user input". Async API: `isAsyncEncryptionAvailable(): Promise<boolean>` (lazy init after `ready`), `encryptStringAsync(plainText): Promise<Buffer>`, `decryptStringAsync(encrypted): Promise<{ result: string, shouldReEncrypt: boolean }>` — [safe-storage.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/safe-storage.md)
- "On macOS, your app should be code signed for `safeStorage` to behave consistently. Without a valid, consistent signature, macOS may not recognize different builds of your app as the same application, which can cause the Keychain to re-prompt the user for permission on every update." — same file
- The v44.4.4 `breaking-changes.md` sections are 44.0 … 35.0 (plus older); there is no "Planned Breaking Changes (45/46)" entry mentioning `safeStorage` — [breaking-changes.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/breaking-changes.md)
- `node:sqlite` in Node v24.21.0: "Stability: 1.2 - Release candidate"; became RC in v24.15.0 (PR 61262), un-flagged since v22.13.0 / v23.4.0 — [nodejs/node doc/api/sqlite.md @ v24.21.0](https://raw.githubusercontent.com/nodejs/node/v24.21.0/doc/api/sqlite.md)
- Electron 44.4.4 bundles Node v24.21.0 — [DEPS @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/DEPS)
- DeepDeck persists browser state as JSON under `app.getPath("userData")` (`browser-tabs.json`, permission/zoom preferences) — `browser-window.ts` line 84; `browser-session.ts` lines 27–34.

### Inferences
- Layout: `~/Library/Application Support/Toolsmith/` (= `userData`) with `toolsmith.sqlite` (sites, tools, versions, verification records), `secrets/` (safeStorage-encrypted blobs for the API-key provider), and Chromium's own `Partitions/sites/` created automatically by `persist:sites`.
- Tool store: content-hashed immutable versions with an active pointer (per Toolsmith's glossary) is relational-shaped; SQLite is the better fit than JSON files. `node:sqlite` avoids the native-rebuild step that `better-sqlite3` needs against Electron's ABI (a well-known cost, not sourced here). If `require('node:sqlite')` turns out to be unavailable in Electron's Node build, fall back to `better-sqlite3` with `@electron/rebuild`.
- Secrets: keep only the provider API key (if the user chooses that provider) in safeStorage; the `claude`/`codex` binaries need no stored secret. Write the encrypted Buffer to disk, never the plaintext; read via `decryptStringAsync` and honour `shouldReEncrypt`.

### Gaps
- Not verified that Electron 44's embedded Node exposes `node:sqlite` (Electron builds Node with its own GN config; some modules are compiled out). Must be checked with a one-line `require('node:sqlite')` in the main process before committing to it.
- The claim "Electron 46 removes the sync safeStorage API" could not be confirmed from any Electron source at the pinned tag; no Electron 46 exists on npm.

## KQ9. Code signing / notarization for a v1 only the author runs

### Takeaway
An unsigned or ad-hoc-signed build runs locally, but Electron explicitly warns that `safeStorage` (Keychain) "may behave inconsistently" without a valid, consistent signature — the practical symptom is Keychain re-prompting after every rebuild. For a single-user v1, ad-hoc signing with a *stable* identifier is enough to develop; a Developer ID signature is needed the moment secrets must survive rebuilds without prompts.

### Cited Findings
- "A number of macOS APIs exposed by Electron rely on system frameworks (like Keychain Access and Squirrel.Mac) that only behave correctly once your app is code signed. When testing these APIs, keep in mind that an unsigned or ad-hoc signed app may behave inconsistently … `safeStorage` — Without a valid, consistent code signature, macOS may be unable to tell that two builds of your unsigned app are 'the same app', which can cause the Keychain to prompt the user for permission again after every update. `app.setLoginItemSettings()` — Login items can behave incorrectly … when the app is not packaged, code signed, and notarized." — [code-signing.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/tutorial/code-signing.md)
- The same note is repeated in the `safeStorage` reference — [safe-storage.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/api/safe-storage.md)
- Electron 44 requires macOS 13+ — [breaking-changes.md @ v44.4.4](https://raw.githubusercontent.com/electron/electron/v44.4.4/docs/breaking-changes.md)

### Inferences
- v1 plan: run from `electron-vite dev` (unsigned Electron binary; Keychain prompts once per Electron binary, acceptable) and package with electron-builder using ad-hoc identity (`identity: null` / `-`) for local DMGs. Keep the one stored secret (provider API key) small so a Keychain re-prompt is a nuisance, not data loss; store nothing else in safeStorage. Move to Developer ID + notarization (`hardenedRuntime`, `notarize` in electron-builder) before sharing builds — no evidence needed beyond the doc above.
- Nothing in the WebMCP/CDP path (`debugger`, `enableBlinkFeatures`, `session`) requires signing; only Keychain-backed `safeStorage` and login items do.

### Gaps
- Whether ad-hoc signing with a fixed bundle ID avoids Keychain re-prompts across rebuilds is not stated by Electron; the doc only says unsigned/ad-hoc "may behave inconsistently".
